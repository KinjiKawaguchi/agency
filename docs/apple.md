# Agency for iPhone

`apple/` holds the iPhone app: native SwiftUI screens that talk to the owner's home node's Client API, and sign decisions with a key in the phone's Secure Enclave.

```
apple/
  AgencyKit/            Swift package: the protocol code, the Client API client, the screens' models and
                        wording, and the SwiftUI screens (AgencyUI). Everything but AgencyUI builds and
                        tests on macOS and Linux.
  Shared/               The app code every platform uses: first-launch setup, the session, the shell's
                        model and screens (`Shell/`), the sign-in, the Keychain, the Secure Enclave key, push,
                        the alert strings. Nothing here imports UIKit or AppKit.
  Mac/                  What is the Mac's alone: the app entry and delegate, the sidebar, the window the
                        sign-in sheet opens over, asking for a push token, the app icon, the sandbox
                        entitlements (the `AgencyMac` target).
  App/                  What is the iPhone's alone: the app entry and delegate, the tab bar, the window the
                        sign-in sheet opens over, asking for a push token, the app icon, Info.plist.
  Config/Shared.xcconfig  Defaults; includes Local.xcconfig when it exists.
  Local.xcconfig.example  Template for the signing values. Copy it to Local.xcconfig (not committed).
  ExportOptions.plist   Export settings for App Store Connect.
  project.yml           XcodeGen project definition.
  scripts/make-icon.swift  Draws the app icon.
  scripts/register-bundle-id.sh  Registers the bundle ID and enables Push Notifications.
  scripts/testflight.sh  Archives and uploads one build to TestFlight.
  scripts/test/run.sh   Offline tests of the two scripts.
```

## How the app behaves

- On the first launch it asks for the home node address and keeps it in `UserDefaults`. Only the origin is kept: a pasted path is dropped. Plain `http` is accepted only for `localhost`, `127.0.0.1`, and `.local` names, so a node on the owner's machine can be tried.
- Every screen is native and reads from the node's Client API (the next section). The app shows no web page. Earlier versions showed the web client in a web view; that web view, its cookie copy of the Access token and the bridge for the page were removed, and the data they left in the app (the cookie and the web client's own storage) is removed once at the first launch after the update (`LegacyWebData`).

Every call to the node's Client API carries `x-agency-client: ios/0.3.1 (202611261830)` (or `macos/…`), the app's platform, its `CFBundleShortVersionString` and its `CFBundleVersion`, so that a node knows which app versions its owners use (agency#318). The node's reader is strict and ignores the whole header when a part is outside its form, so the app sends only what is in it: the version exactly three numbers, the build only digits (a build that is not digits is left out and the version is kept), and no header at all without a version. The browser's sign-in handoff is not a Client API call and carries none.

## The native desk

- **The tabs** (five, the most a phone's bar shows without folding the rest into "More") are 決めること, 全体, 組織, 成果 and 端末, all native; 組織 holds the org chart and the participants and work behind a switch at the top, and 成果 holds the costs and the evaluation behind one, as the web client groups them. A screen is a case of the shell's `Tab` and of one switch (`screen(_:session:)`).
- **Calls to the node** go through `NodeClient` (`AgencyAPI`) over `URLSessionTransport`, which never follows a redirect: Access answers an ended session with one, and the app then runs the sign-in again. The Access token that the sign-in hands over is kept in the Keychain (`AccessTokenStore`, this phone only, not synced) and sent as `cf-access-token`.
- **The device key** is a P-256 key made inside the Secure Enclave (`SecureEnclaveSigner`). No process can read it. It signs only after Face ID, each time, and only while the current set of faces is enrolled: adding or removing a face destroys the key, and the phone is added again. The Keychain keeps an opaque handle to the key, not the key. A phone without a Secure Enclave or without Face ID set up cannot decide; it can still read. The settings can make the key again, for when a change of faces left the old one unusable. **A stored key is never replaced by the app on its own** (`KeyLoader`, agency#477): a new key is made only when the Keychain says there is none (`errSecItemNotFound`); any other failure to read the handle (a locked phone, `errSecInteractionNotAllowed`, a busy store) or to open it is tried again a few times, and then reported (「この端末の鍵を使えません」) with the system's reason (also written to the log, never a key) on a card at the top of the Devices tab with two buttons: try again (it is also tried again when the app comes to the front) and make the key again (the settings' choice, after a confirmation); the desk says that nothing can be decided meanwhile, and everything else can still be read, since only deciding and the devices need the key. The key is read without holding the main actor while it waits, and a handle that was stored by another run between the read and the add is read, not reported as a key that could not be made. The Keychain's answers for the key are decided by `KeychainStatus` (only `errSecItemNotFound` is "none"; a refused delete is a failure, so that making the key again cannot do nothing and say it did, and the person is told, the key staying), and `KeyStoreGuardTests` fails if a write over a stored item (`SecItemUpdate`/`save`) comes back on the key path. A new handle is added to the Keychain, never written over one (`KeychainStore.add`, which fails for a duplicate), and the old handle is kept until the person chooses to make a new key. The key is one for each home node host, so the same node under another address is another key and another device on the list (nothing is deleted). There is one key, one Keychain token and one set of drafts for each home node host, never shared between nodes, so a second home node later is a second session and not a rewrite.
- **Adding this phone.** A key signs decisions only once it is added to the org. The desk shows a card that says so, asks the node to add this phone (`POST /api/devices/requests`) and shows the pairing code (`xxxx-xxxx-xxxx`, from the key's fingerprint, the same as the node's). The owner compares it on a device that is already added, or at the node's terminal, and adds the phone there. Until then the desk can be read, options picked and text typed, and nothing can be sent. A browser's key (the web client's) is a different device; both can be added. While it waits, the card says exactly how it gets approved (agency#157): when the account already has devices, the labels of those devices ("open Agency on <labels> and approve it under Devices"), and when it has none, the command for the node's machine, which is the one the node gives in the device list (`node.command`, shown as text, never run, ignored when empty, over 500 characters or holding a control character) and otherwise `agency device-add`. The code is large, one line says what comparing it protects against, and the card asks the node again every 4 seconds, on the desk too, and goes away by itself once the phone is added.
- **The devices tab** (端末) shows this phone's pairing code and whether it is added, the person's devices (one row for a device in several orgs, the newest first), and the devices that asked to be added. Confirming one signs a device change (`DeviceChangeSender`): for each org that lacks the new device and holds this phone, a change `{ org, account, op: add, device, at }` is stamped with the node's time, signed with Face ID as this phone's own id in that org, and posted to `/api/devices/changes` (one Face ID prompt for each org). Before anything is signed the phone checks the request against its own key: the id and the code the node showed must be the ones the key makes, because a node that showed another code would have the person compare the wrong one and add a different key. Face ID is also the answer to adding a device from a phone: no other path signs for the person.
- **Sending** (`DeviceDecisionSender`): the envelope comes from the request's own `answerWith`, is stamped with the node's time from `GET /api/session`, is checked for the shape the node requires, and is signed after Face ID, which names the action and the request's title. The node's own device id for this key is read from the device list and used as the signer.
- **Answering for someone** (agency#196, #379). A request addressed to a seat or an external party that the viewer answers for is the viewer's (`mine`), and the node says whom it is for: `TeamSnapshot.relayedFor`, by request id, with the label as the org's definition has it. The desk row and the request screen say "{label} の代理で答える" (the web's words; the glossary's *answer for*, never *relay*), and the decision log says "{label} の代理で答えました。" from `DecisionEntry.relayedFor.label`. The label is read once, at the wire, with the node's hidden characters shown as `?` (`NodeLabel.shown`, also for the values of `relayedFor`, never for the request ids that are its keys). The label has a line of its own on the row (the meta line is cut after two lines) and is shown as the text it is (never read as markup), whole and wrapped, without the spaces around it; an empty one, or one of only spaces, makes no line. The decision itself is sent exactly as before: the node works out for whom it answered, and refuses a client that says it (`DeskItem.answersFor`, `DecisionEntry.answeredFor`). A team on another node says it too (#412): the team's node lists the seats and external parties the reader answers for, the home node keeps that with its copy of the team and takes each label from its own definition of the org, and the snapshot's `mine` and `relayedFor` hold those requests like a local team's. A reader the team does not address (no `viewer`) has only those requests, and the desk shows them with the same line; nothing here changes for the app, which reads the same fields. A decision for such a team goes to its node as before, and the log's label is the home node's last copy at the time it was sent, so one sent before the node had read the team is logged without it.
- **Deciding and moving on** (agency#447, the twin of #446; the contract is AgencyWeb's on #446). Deciding signs the reply (Face ID), **keeps the signed envelope on the device** (`DecisionOutbox`, a file for each home node in Application Support, written atomically before the desk moves on, readable after the first unlock, left out of backups), takes the item off the pile and opens the next one at once. The node is told from the outbox, in the background of the screen, and the owner does not wait: any 2xx is "taken" (`applied`, `delivered` or `queued`) and the entry leaves; a failure that sending again may mend (no network, 5xx, 408, 425, 429, a timeout) is retried by itself after 5 s, 15 s, 1 min, 5 min and then every 5 min, **the same envelope with the same id** (a repeated id is kept once by the node); 400, 401, 403, 404, 409 and any other 4xx stop, with the node's own reason, and wait for the owner; an ended Access sign-in pauses all sending and drops nothing. A decision is signed without waiting for the network: the account, this device's id in each org and the node's clock are read once and kept for ten minutes (the first decision of a run, or one after ten minutes, reads them; with the network down what was read before is used). The pile and the counts leave a decision while it is kept, in flight, failed or `queued` in the node's decision log (the node's own view lists the request until the team applied it), and a decision that the team's node refused later is back. The sending tray (「送信中の決定」) on the desk lists what is in flight and each failure with its reason as given, 「もう一度送る」 (the same envelope again, on every entry that did not get through) and 「破棄」 (on one that stopped: the item returns with what was typed and picked). There is no Undo. A signed entry is kept until the node takes it or the owner discards it, so a device is not to be removed while one is kept (`DecisionOutbox.hasSignedEntries`; the apps do not remove a device yet). Forgetting a home node removes what was kept for it. Not in this change: sending when the app goes to the background and on a wake (a later step), and the `Retry-After` of a 503 (the client does not read headers yet).
- **Push** is registered by the app itself (`POST /api/push/tokens`) once the desk loads, and the badge is the number of requests waiting on the owner. A tapped notification opens that request on the desk.
- **One shared read** (`SnapshotCache`): the desk, the overview, the participants and the costs screens all read the account and every team's view. They read through one cache in the session, so the app asks the node once for what several screens want and the screens do not disagree for a moment. A read within five seconds of the last is answered from it, two reads at the same moment cause one request, and a failed read is not kept. A decision drops what was read before it (`invalidate()`), and a read that started before the decision does not become the cache. A team that was read keeps its last answer on the desk when a later read of it fails, and its failure is still reported.
- **Settings** (the gear on the desk) show the home node and change it. Changing it forgets the token.

## The native overview

The overview tab mirrors the web client's Overview screen (`web/src/overview`): every org and team the account sees on one screen, with the funding sources' usage below. `AgencyModel/Overview` holds what it decides, ported from the web with its test cases:

- `TeamSummary` says what a team needs from the viewer: **mine** (the node's `mine` list is not empty, however busy the team is), **stuck** (work is blocked, counted by the reason the runtime gives), **idle** (participants, none working) or the rest. The viewer is not counted among the participants. Whose a request is stays the node's call.
- `OverviewOrder` puts teams in the order mine, stuck, unreadable, idle, the rest, still loading; within a rank the team with more waiting or more blocked comes first, then by name. An org stands where its most pressing team does.
- `WindowForecast` projects a funding window to its reset from the pace so far, and `FundingSummary` lists the weekly window before the five-hour one. A window whose reset has passed has no forecast.
- `OverviewStore` reads `GET /api/me`, each team's view and each readable team's usage over 7 days (`NodeClient.usage`), and keeps each team's own outcome: a team that cannot be read is shown as that, in its place, and a team that was read keeps its last answer when a later read fails. A team whose node cannot be reached is not asked for usage (a 404 means its runtime reports none).

The views are in `AgencyUI/Overview`; a long team name is cut after two lines and opens in full when tapped.

## The native participants and work

The tab mirrors the web client's participants and work screen (`web/src/people`), one section for each team the account can read: the participants without the viewer (face, what they do, since when, what they hold, and for someone who waits on the viewer, the request that stops them), the work in progress with its forecast, the work that cannot move with its reason, and the epics with their bars and forecasts. `AgencyModel/People` holds what it decides, ported with the web's test cases: `Work` (the bar of an epic, the order of epics, which work is in progress and which is blocked), `Identity` (the color and letters of a face, the same hash as the web), `PeopleSection` and its rows, and `PeopleStore`. Whether a participant waits on the viewer is the node's list (`waitingOnViewer`), as on the desk. A finished epic (`doneAt` present, or every child done) is shown as finished with the time it finished and no forecast, after the open epics. A long list shows its first rows (eight for work, six refs for a participant) and the rest open on a tap. `TeamReader` is the one place that reads every team's view for the overview and this screen.

## The native costs

The tab mirrors the web client's costs screen (`web/src/costs`): the funding sources, each with its weekly and five-hour window projected to its reset (the same cards as on the overview), then, for every team the account can read, its token use over 7, 14 or 30 days, priced as if billed by the API: three figures, the cost by day stacked by participant, and a card for each participant. `AgencyModel/Costs` holds what it decides, ported with the web's test cases: `UsageChart` (the series in the team's own order, each participant's fixed color slot with the ninth and later folded into "other", the columns and the totals), `TokenReport`, and `CostsStore` (a team whose runtime reports no usage answers 404 and says so; 503 says the team could not answer just now; any other failure is shown as that). A table of five columns would be wider than a phone, so each participant is a card. A tap on a day shows what each participant cost on it, and a long name is cut and opens in full when tapped.

## The native evaluation

The evaluation page of 成果 mirrors the web client's (`web/src/evaluation`): for the org chosen (the first, or one of several) and a period (14, 30 or 90 days), each team's headline numbers (new features and pull requests merged, the lead times with their median and p90, how long main was red, reverts, the cost per merged pull request), then each of them over the days: the merged pull requests stacked by type, the lead times and the cost per merged pull request as 7-day trends, main's red time and the reverts per day. Below, where each team's effort goes (`GET /api/orgs/<org>/effort`): its cost by work type as bars with the org's intended share marked on the same track and the gap in points, the last seven days against the weekly budget, the cost by day stacked by type, and the numbers in a table. The numbers are the node's: the screen only draws them, and the same route is what an agent cites. `AgencyAPI` reads the answers the way the web client does (`Evaluation`, `Effort`: a type left out counts as 0, a negative or non-numeric number refuses the whole answer, each team has its own `from` and `until` and is drawn against them), and the shared samples `testdata/evaluation.sample.json` and `testdata/effort.sample.json` are decoded in the tests. A pull request that reverts another counts in `reverts` and not in `merged`; the pull requests merged are both, as the node's `costPerMergedPrUsd` divides by. The org's plan is `teams[].plan` of the org definition (`OrgPlans`): only whole shares that sum to 100 and a whole budget are a plan, anything else is "no plan stated". A node that does not serve the routes yet answers 404 and the screen says so. A tap on a day opens what each series was on it. `AgencyModel/Evaluation` holds what it decides, ported with the web's test cases (`EvaluationSeries`, `DurationFormat`, `TeamEvaluationReport`, `EffortAnalysis`, `TeamEffortReport`, `EvaluationStore`).

## The native org chart

The org chart page of 組織 mirrors the web client's (`web/src/org`, the chart of every org of agency#145): with several orgs and none chosen, every org under the account, each with its departments (nested by parent), its teams and its members; with one org (or one chosen), that org's own chart, and a department opens its own chart ("back to the whole organization" returns). On a phone it is the indented list the web draws on a small screen. Each team's box carries the overview's signals, worked out by `TeamSummary` so the two screens cannot disagree: the requests that are the viewer's (the node's `mine`, rolled up into each department and org), stuck, idle, how many participants work, its participants as faces (six, then "+N"), and "old data" when its data is a copy that could not be renewed; a team that could not be read says so in its box, one still being read is grey bars. An org whose definition cannot be read is shown as such and the others are still drawn. A tap on a team opens the desk when it has requests waiting, else the overview. It reads `GET /api/me`, `GET /api/orgs/<org>` for every org (`OrgDefinition`) and the team views the overview reads (`TeamReader`, with the retry rule of the page above); a node route that combined them would save the phone those reads but would be a protocol addition. `AgencyModel/OrgChart` holds what it decides, ported with the web's test cases (`OrgTreeBuilder`, `OrgChartRow`, `TeamBoxText`, `OrgChartStore`).

## The Mac app

The `AgencyMac` target (macOS 14.4 or later, the same reason as iOS 17.4: the https callback of the sign-in session) is the same app on a Mac: the same session, screens, news, and push kinds from `Shared/` and the package, a sidebar instead of a tab bar (`Mac/HomeShell.swift`), and the sandbox of the Mac App Store, because it is distributed through TestFlight for Mac and not outside Apple (no Developer ID, no notarization). It has the iPhone's name and bundle ID, so it is one record in App Store Connect with the Mac added, and the node's association file (`access.appId`) and push topic need no change.

- **The key.** Each Mac makes its own P-256 key in the Secure Enclave, one for each home node, and is added as another device through the same pairing (approve it from a device that is already added). The rule differs from the iPhone's on purpose: the iPhone's key needs Face ID alone (`.biometryCurrentSet`); the Mac's key needs Touch ID **or the Mac's password** (`.userPresence`), because a Mac may have no Touch ID, or be used closed with an external keyboard, where a Touch-ID-only key could never sign. It is still a Secure Enclave key that cannot be read, and each signature still asks for the person. `.biometryCurrentSet` is not used there: Apple documents it as needing Touch ID to be available and enrolled, which is the case the rule exists for, and with the password as an alternative, tying the key to the current set of fingers would protect nothing. The settings and the confirmation lines say "Touch ID か Mac のパスワード" there.
- **Keychain.** The Mac uses the data protection keychain (`kSecUseDataProtectionKeychain`), which the sandboxed app reaches through its `keychain-access-groups` entitlement; the login keychain would ignore the accessibility class and ask the person for access.
- **Push and the Dock.** The same coordinator asks for permission and registers for remote notifications (`com.apple.developer.aps-environment` in the entitlements); the push label is `Mac`, never the computer's name. The badge on the Dock icon is the number of requests waiting.
- **The menu bar.** A menu-bar item (`MenuBarExtra`) shows a tray symbol, with the number of requests waiting when some do (the same number as the desk tab and the Dock badge), and a menu with that count, "Agency を開く" and "Agency を終了". Closing the window leaves the app running with its session: the session belongs to the app (`MacAppModel`), not to the window, and the desk is read every 30 seconds for as long as the app runs, so the item and the Dock badge keep following it. The item says which of four things is the case (`MenuBarState`): no home node entered ("ホームノードが設定されていません"), a home node and not answered yet ("まだ読み込んでいません"), a first read that failed ("読めませんでした", dim), or the count (`DeskStore.knownWaitingCount`, 0 included). When a read fails after a number was known, the number stays but the item is dim and the menu adds a line saying it is not the latest, so a failure is never silent. The news (banners) is polled only by the window: a banner nobody can see is not news. It shows the count only, never a title.
- **Settings.** ⌘, in the app menu opens the settings sheet of the window in front (the same sheet as the gear).
- **Not on the Mac yet:** the widgets.

### Getting the Mac build to TestFlight

`apple/scripts/testflight.sh --platform macos` archives the `AgencyMac` scheme for macOS and sends it to the same app record as the iPhone's. What the App Store Connect API can and cannot do for the Mac is not fully documented by Apple, so `apple/scripts/register-bundle-id.sh` only *reports* what it finds about the Mac and changes the one thing it is told to. These steps are the owner's, in this order; the script prints which of them are still open:

1. **The bundle ID.** The script registers or finds the iPhone's bundle ID and its capabilities (Push Notifications, Associated Domains, App Groups). It then asks the API for a *macOS* bundle ID of the same name and says whether there is one. It never creates one: the API's `UNIVERSAL` platform value is documented but reported to be refused, and a second record is not what a universal purchase wants. If the first Mac archive fails with a signing error that names the identifier, open Certificates, Identifiers & Profiles, Identifiers in the developer portal, create the macOS identifier for the same string with the same capabilities (Push Notifications, Associated Domains), and keep the error text.
2. **The macOS platform of the app record.** In App Store Connect, open the app, choose Add Platform in the sidebar, then macOS. Or run the script again with `ADD_MACOS_PLATFORM=1` (it posts an App Store version with the platform `MAC_OS` and the app's own `MARKETING_VERSION` from `project.yml`, so no empty version of another number stays on the record; `ASC_MACOS_VERSION` names another). A read of the report that this key may not make is skipped with a message, and nothing is added when it could not look. **This cannot be undone:** once the app has two platform versions approved it is a universal purchase for good. That is why the script never does it without the flag, and why the owner decides.
3. **Certificates.** A Mac App Store build is signed with Apple Distribution and its installer package with Mac Installer Distribution. `-allowProvisioningUpdates` with the API key should create both; if the export says a certificate is missing, create it in the portal (Certificates, +, Mac Installer Distribution).
4. **The build.** `ASC_KEY_PATH=… ASC_KEY_ID=… ASC_ISSUER_ID=… apple/scripts/testflight.sh --platform macos` (the iPhone's is the same command without the option). The API cannot upload a build; the export step does.
5. **Install.** In App Store Connect, TestFlight, add yourself to an internal group for the macOS build; on the Mac, open the TestFlight app from the Mac App Store and install it.

What no script and no test here has seen, and the first build must answer (the owner's list): the sign-in sheet and its return to the app, the Touch ID or password prompt when the key is made and for each signature, adding this Mac from the iPhone (compare the code, approve), a banner within 30 seconds of something new, a push for a device or a refused decision and its tap, the Dock badge, the menu-bar count, ⌘, for settings, and quitting and opening again with the window closed.

## A read that is not ready yet

A node answers 503 for a team's view while its board is still being read (and for its usage when the team's runtime does not answer in time), and a slow node times out. The native screens that read team views (the overview, participants and work, costs) do not show that as a failure (agency#170, the same rule as the web client). `RetryPolicy` asks again after 1, 2, 4, 8 and 15 seconds for the answers that say "not now" (408, 429, 502, 503, 504, and a read with no answer at all); every other refusal, a 404 and the ended sign-in are final and shown at once. While a team is not ready its card is grey bars (a skeleton), and the other teams are shown as they arrive. What is on screen stays when a refresh fails. Only when the retries are used up does the region say what could not be read, why (the node's own words) and that it asks again 30 seconds later, with a "Try again" button; one region failing never blanks the screen. A screen that is shown reads again every 30 seconds.

## Nothing stands in for an answer (agency#303)

A screen never shows a value the node has not given: a `0`, an empty list or a default before the answer makes "not read yet" look like "really nothing". Until the node has answered, a screen shows grey bars (a skeleton) in the place of the content; when the read fails and nothing was read before, it says so and why. What was read before stays when a later read fails. The desk has `hasAnswer` (a team was read, or a read finished) and `knownWaitingCount` (`nil` until a read has finished, `0` only when the node said nothing waits); once a read has finished the desk stays answered, so a refresh under way or a failed one keeps the pile and the number; a place outside the window that shows the number (the Mac's menu-bar item, a badge) uses the optional one. What the node says about itself (`hidesTitles`, whether it sends the kinds of notification) is optional until it has said: the widgets show no title, and the settings claim nothing, until then. The same holds for the other screens (agency#314): the overview, the costs, the org chart, the participants and work, and the evaluation each have `hasAnswered`, set once when a read has finished and never reset, so an account with nothing in it keeps saying so through every refresh instead of going back to bars every 30 seconds, and a failed or a cancelled refresh leaves what was shown. A read that was cancelled (the Mac's sidebar cancels a screen's read when another is chosen) leaves the state as it was and is never shown as a failure.

`NoStandInValuesTests` reads the sources of the screens, the widgets and the app for `?? 0`, `?? []`, `?? ""`, `?? false`, `?? true` and state that starts as a number or `true`, and fails for any that is not named in the test with the reason it is not a stand-in.

## The outcomes page (agency#206)

The owner's numbers for what each org measures (`GET /api/orgs/<org>/outcomes?days=`) and how a KPI stood around the day the epic an aim names shipped (`.../outcomes/readings`), as the web client shows them. `OutcomesStore` reads both for every org of the account.

- **Owner only.** A node answers anyone else 403 (and an org it cannot answer 404): the org is left out and nothing says why. The page is offered only after a read has let the owner see at least one org (`isAvailable`): not while it loads, not on a refusal, not when the read failed before one ever worked; once one worked it stays, until a read finishes with every org refusing. A failed refresh keeps what was read and says it failed.
- **Business data.** The numbers are in memory only: not in the cache that the screens share, not on the disk, in a widget, a notification or a log, and they go with the session.
- **What a card says.** The latest number of the period by its KPI's unit: money in its own currency (an ISO code, never converted), a percent as it is (never clipped), a count grouped, a ratio with its `×`, a duration as the evaluation writes one; a unit this app does not know is a plain number. The movement is read from the baseline (`before`) to the latest number, with a word and a tone by `goodWhen` (a direction the node does not say colours nothing). A KPI with no number in the period but one before it shows that one as older; a KPI with none shows a gap. A 0 the node gave is a 0, and a missing number is never one.
- **Readings.** One line for each aim, in the words of the state (`ready` gives the two numbers, the change and a line that the figure moved after the work and that this does not say the work moved it; every other state says what is missing). A test fails if any of the page's words claims a cause.
- **Entering a number** (agency#363). `OutcomesStore.enter` checks what was typed as the node checks it (`NumberCheck`: a real calendar day, at most one day ahead of the node's day, `Outcomes.until`, and not older than ten years; a decimal of digits, a sign and a point, never `0x1F`, `1e3` or `inf`, at most 1e15; a note of at most 200 characters, counted as Unicode scalars, with no control character), sends it once (`POST …/outcomes/observations`, the write token and its renewal as for any write, the body plain JSON because the value is a decimal), says the node's refusals in words (409 full, 403 owner only, the node's reason for the other 4xx, the usual failure for the rest), and after a save reads the numbers and the readings again, and every history that is open. A second number for the same day replaces the first in every reading and the first stays in the history.
- **The screens.** Each KPI's card has a button "数値を入れる" that opens a sheet (a day picker, the number, an optional note, in which unit to write it, and that a second number for the same day replaces the first), and "履歴を見る", which opens the history under the card. The sheet says what is wrong before sending, says the node's refusals in its words, and stays open after a save for the next number. The day picked is a calendar day carried in UTC, so the day sent is the day picked. The same on the iPhone and the Mac. The sheet is covered, like the page, whenever the iPhone app is not in front.
- **The history** of a KPI (`GET …/outcomes/observations`, newest first, replaced entries included) is read when it is opened and kept only while it is open; an entry a later one for the same KPI and day replaced is marked (times compared as instants, not as text). The words are the web's.
- **The period** is 90 days by default (a monthly number is rarely in 14), or 30, the same on the web.
- **The screen.** A third page, 成果の指標, in the 成果 tab beside the costs and the evaluation (`ResultsScreen`, the same on the iPhone and the Mac), offered only while `isAvailable`: with the node refusing the owner nothing in the tab changes and nothing says why. Each KPI is a card (label, the latest number, the day it is as of, the movement as a symbol, words and colour, and its numbers as dots on their days joined by a line, with nothing for a day without a number); then the readings. Until the node has answered, the page is grey bars, not an empty page; a failure is said over what was read. The numbers are shown on a plain cover whenever the iPhone app is not in front, so that the picture the system keeps for the app switcher holds none of them (not verified on a device).

## A started recovery of an org (agency#360)

When `/api/me` gives an org a `recovery` (`OrgRef.recovery`: `takesEffectAt`, `newRootKey`, `replacesRecoveryKey`), the desk shows it at the top, one item for each such org, on the iPhone and the Mac: "<org> のルート鍵の回復が始まりました。<time> に有効になります。心当たりがないときは、ルート鍵のノードで取り消してください:" and the command `agency root-cancel-recovery --org <id>` (selectable), with the new root key and the replaced recovery key when the node says them. That is for the owner of the org's root key (`OrgRef.isRoot`), who can cancel it; every other member who lists the org is told too, because a root change concerns everyone whose trust follows it, in words that give no command: "<org> のルート鍵の回復が進んでいます。<time> に有効になります。取り消せるのは、そのルート鍵の持ち主です。" It has no way to dismiss it: the owner can cancel only while it waits, so it stays for as long as the node says it waits and goes when the node stops (cancelled or taken). A failed read leaves it. The words are the web's and the glossary's (ルート鍵の回復, 回復用の鍵).

The node's push of the kind `recovery` (`agency: { type: "recovery", org }`, its title and body written by the node) reaches every token whatever kinds the app registered with, and the app asks the system to show every notification it gets, so the notification settings do not hide it; tapping it opens the desk of the home node that is current. The push does not name its node (agency#117), so with several home nodes the recovery may be on another one: its item is seen once the owner has switched to that node.

The cancel command is built from the org's id, which the node gave, and is made to be pasted into a terminal, so it is shown only when the id is one the node itself would have made (its `Id` rule: lower-case letters, digits and hyphens, not starting with a hyphen, at most 40, the web's rule too); otherwise the item says in words where to run `agency root-cancel-recovery` (the web's sentence).

## The cost under the outcomes (agency#77)

Under each KPI that has numbers in the period, the outcomes page draws what the org's work cost on the same days, as the web does (`CostOnTheseDays`): columns of the API-priced cost, so that a movement can be read next to the effort of its days. It comes from the evaluation (`GET /api/orgs/<org>/evaluation?days=<the days the KPIs are drawn over>`), read **after** the numbers are on screen, because an evaluation asks every team's runtime and is slow; until it is read a quiet bar stands in the place, and a cost that cannot be read says so (「この期間のコストを読み込めませんでした。」) and leaves the numbers alone. A read cost is kept for five minutes (the page refreshes every few seconds); one that could not be read is asked for again at the next refresh; another period drops it and reads its own.

A day is the sum of what each team reports for it, and a team reports a day when it lies inside its own period (`from` to `until`): the node leaves out of `byDay` a day with nothing in it, so a day inside the period that `byDay` omits is a day of 0 (a sliver in the accent colour), while a day inside no team's period has no cost (a grey mark), which is not a cost of 0. A team that did not answer is counted and the sum is said to be of the others (「報告できなかった N チームを除きます。」). A tap on a day says its date and its cost in words, and a screen reader gets all of them.

## The node's own response times (agency#240)

The evaluation screen ends with 「このノードの応答時間」, for the owner only, from `GET /api/metrics?days=1|7|30` (`docs/protocol.md`, "Metrics"; the web's twin is the same section of its evaluation page, in the same words). A 403 (not the owner) draws nothing at all, with no alert and no hint, and the section stays gone; a 404 says in one line that the node does not measure; an answer with no series says that nothing was measured in the period, which is not 0 ms. Until the node has answered the first time only a skeleton is drawn (no heading, so that a viewer who is not the owner sees none flash and go); another period keeps the heading and shows a skeleton in place of its numbers, each period keeps its own answer (7 days are never shown as 1), and a failed refresh leaves what was shown. A node that cannot give its measurements, or whose answer cannot be read, is told plainly (「ノードが計測を返せませんでした。」), without the reader's own words.

- **In-node reads against the budget** the node names (`budget.inNodeReadP95Ms`): one verdict and the reads that break it. A p95 is known only as its bucket, so there are three outcomes: within (the bucket's top is at most the budget), over (its bottom, or 30 s for "beyond", is at least the budget) and otherwise undetermined (「予算に対して判断できません」): a budget inside the bucket is neither kept nor broken. Only series the node says are `isInNodeRead` count. No budget named, no budget card.
- **Objectives** the operator set, as the node states them (`met`, `notMet`, `undetermined` and `unknown`, and what it measured): the app compares nothing. `undetermined` (「この目標に対して判断できません」) is an objective that falls inside the bucket the p95 is known by, so the measurement cannot say: the same three-outcome rule as the budget; `unknown` (「まだ判断できません」) is no call in the range, or a state the app does not know. They are drawn when the node gives any.
- **Routes by route group** (the node's `group`; the app owns only the group names it says in Japanese, and says the node's word for another) and **the calls the node makes**, each group opening to its routes, with p50, p95, p99, requests and errors.
- **Every percentile is "at most"** (「以下」): it is the upper bound of its bucket, and one beyond the last bucket (30 s) is 「30 秒 より遅い」. A group's percentile is read from its series' buckets **added together** (nearest rank, as the node reads it), never an average of percentiles; a test pins it against every series of the shared sample (`testdata/metrics.sample.json`). A series whose buckets deny its count, or that has more errors than calls, refuses the whole answer. A row with no duration shows no percentile cell, not a dash.
- **The p95 hour by hour** (the web's 「時間ごとの推移」, from `byHour`): one small chart for each route group, first the in-node reads against the budget (a dashed line, on that chart only), then each group of routes and each group of calls, busiest first. Periods of 1 and 7 days are read with `&hourBuckets=1`, so that each hour carries its 15 buckets; the 30 days come with totals only and the card says so (「ノードが時間ごとの数字を返すのは、7 日までの期間です。…」). An hour whose buckets deny its count (or are not 15 non-negative numbers) refuses the whole answer, as a series' do. A chart's point is **the group's own p95**, read from the hour's buckets of all its routes added (nearest rank), when every route that had calls in every hour gave buckets; otherwise **every hour of that chart** is the slowest route's p95 (the group's own is at most that), so that one line never mixes two meanings, and the chart says so; a route with calls and no p95 makes the hour 「30 秒 より遅い」 (a hollow mark at the top). An hour with no call is a gap in the line, never a 0. One axis, in milliseconds, on a log scale from 0.5 ms to 30 s. The node's hours are UTC hours; they are written in the device's time zone, and the two labels under a plot are the start of the first hour and the start of the last. The budget is named above the plot (「予算 …」, beside a dashed mark) and drawn as a dashed line across it, so that its name never runs into the plot at a large text size. The in-node reads are drawn twice, as on the web: once against the budget (all of them), and once in their own route group. For VoiceOver each chart has a sentence and, under 「時間ごとの数字を見る」, a table of the hours with calls, newest first. The scale, the choice of exact or approximate and the rows are in `AgencyModel` (`HourTrend`, `HourScale`, `HourChart`), and `testdata/metrics.sample.json` is read against them.

## Removing one of the owner's devices (agency#442, #443)

The Devices screen has a 「削除」 button for each of the person's devices, this phone's too, as the web does (agency#442, with the web's words). A removal takes the device's key out of an org for good (the protocol's `op: remove`; the key is added to `revoked` and can never sign again, under any id), and it is **signed by this device** with its Secure Enclave key after Face ID or Touch ID (the prompt names the device, and it is asked once for all the orgs: one `LAContext` signs every change, which are all made and signed before the first is sent), as an approval is: for each org that lists the device, one device change, signed as this device's own id in that org, and sent with `POST /api/devices/changes`. **What is signed is the device's id as the node gave it**, and labels are shown through `NodeLabel.shown`.

- **One confirmation** names the device by label and pairing code (from its key), says that it can never sign again, and says in which orgs when there are several.
- **The person's last device in an org is not removed from the app**: nobody could sign for them there, and the node does not stop it, so the rule is the client's, per org: if it holds in any org nothing is removed, and the text says where and points to `agency device-add` on the node's machine.
- **An org where this device is not added** cannot be signed for: the device stays there, the confirmation says so, and the others are removed (and with no org this device can sign for there is nothing to remove).
- **This device itself** is its own case with its own sentence: after the removal this phone's key can never sign again and cannot be added again. When the removal **took effect** (not while the root's node holds it) the app deletes that key and makes a new one (the way the settings' key reset does), and the Devices screen says that the new key is not added yet; the person asks to add it from the screen.
- **The outcome is an open enum**: `applied`/`delivered` took effect, `queued` says the node is asleep, `pending` is said as asked, with the command `agency root-sign` (「ここでは削除を依頼しました。…」) and kept on the device's row, and any other outcome is shown with the node's own message, or when it has none, with 「ノードが、このアプリの知らない答えを返しました。結果は端末の一覧で確かめてください。」: an unknown outcome is never a success (the same for adding a device), and the list is read again. A refusal says why. A device **leaves the list when the node stops listing it** (not before, and not while it is held); a later org's failure keeps what an earlier one held.
- **The list is read again before anything is signed**, and the plan is made again from it: a plan that is not the one the person confirmed (a device was added or removed meanwhile, so the last-device rule may now hold) is not carried out, and the person is told to confirm again. A list that cannot be read signs nothing.
- **This device waits while decisions are kept on it** (decisions signed with its key and not yet sent): its removal would make each of them fail for good. `DevicesStore` takes `hasKeptDecisions`; the confirmation says so instead.
- A new key is made after this device's own removal only when **every** org took it: not while the root's node holds one, and not when one failed (the key still signs there, and it can be tried again).
- The #303 rule holds: the buttons are offered only once the node's list has been read.

## Whether APNs takes this phone's notices (agency#386, #409)

The node keeps, for each push token, when APNs last took a notice (`lastSucceededAt`) and the last time it did not with the reason (`lastFailure`: the status and the reason code APNs answered, or that it could not be reached, never APNs' own words), in `GET /api/push/tokens`, where each token is shortened to its last 8 characters. The Devices screen finds this phone's own token by those 8 characters and says, with the web's words for a browser (`notices.os.push`, APNs in place of the browser's push service):

- **failing**: the last refusal is later than the last taking (compared as times, an offset is not a later time), or there is a refusal and no taking: 「この端末へのプッシュ通知を、APNs は最後に受け付けませんでした（日時）: 理由。ノードは最大 1 日のあいだ再送します。…」 with a warning symbol, then when the last notice was taken, or 「まだ 1 件も受け付けていません。」 ("never" is a missing value, not a date);
- **nothing at all** when APNs takes them (a refusal older than a taking is not one), when the node lists the token with neither fact (that is not "refused": an older node records none, and a new phone may have been sent none), when this phone's token is not among the listed ones, before Apple has given this phone a token, and when the node cannot say (an older node; a failed read leaves what was known). A time the node writes that cannot be read is not a later time, so a refusal stands, and is said with the node's own text for it.

The list is read when the screen opens, on a pull to reload, and again no sooner than 30 seconds later (the screen asks every few seconds for its devices). The reason is the node's own text and is shown as it is.

## Labels from the node are shown without what can reorder them

A label the node gives (an org's, a team's, an account's, a participant's, a KPI's, a device's, a home node's, what a held root change names, and whom a request is answered for) is shown with its hidden characters replaced by `?`, as every client does: the control characters (Unicode category Cc), the line and paragraph separators (U+2028, U+2029), the bidirectional controls (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069), and the format characters that are invisible or change how a line is laid out (the soft hyphen U+00AD, U+180E, U+2060 to U+206F, the zero-width space U+200B, the byte order mark U+FEFF, U+FFF9 to U+FFFB and the language tag U+E0001). The zero-width joiner and non-joiner, the emoji tag characters and the format characters of a script's own text stay; `testdata/label-hidden-chars.json` is the set. The node refuses them in a new label and prints an older one's as `?` in its own text, but a label stored before that can still hold them, and a bidirectional override can reorder the line it sits on, on the screen where the owner decides.

`NodeLabel.shown` (`AgencyProtocol`) does it, and the property wrapper `@Shown` applies it when a label is decoded, so that no screen can show one by forgetting: every `label` of the wire types has it, and so have the fields a held root change names and a participant's name. The text agents write is shown the same way, because a bidirectional override in a request's title can reorder the line the owner decides on: a request's title, an option's text, an agent's status, a work item's and an epic's title (`@Shown`, which also turns a line break into `?`: they are one line), and a request's context and document, an option's detail, a thread's messages, a decision's text, and the message the node gives for a queued decision or device change (`@ShownText`, the same set except that a line break, a carriage return and a tab stay, since these are written in lines). **What the app sends back to the node or signs is the value the node gave, never the shown one**: a display transform must not change what is signed, or the signature covers bytes nobody sent. The three fields that are shown and sent back (the label of a device that asks to be added, which the change that adds it signs; a request's title and the chosen option's text, which go with a decision for the decision log) have a twin that is what was written (`rawLabel`, `rawTitle`, `rawText`, the wrapper's `$field`; only these keep the raw value, in `@ShownWithRaw` and `@ShownTextWithRaw`), and the sending reads the twin; what the person reads in the Face ID prompt is the shown text. `ShownLabelsGuardTests` names each of them and checks the twin and its use, and also fails for a string inside a case of an enum of the node's words (`DecisionState.queued(lastError:)`, `.refused(message:)`, the replica's `error`, an observation's connector `name`, and `NodeError.http(message:)` that an alert reads), which is shown where it is decoded or made, and for a field of the wire types named `title`, `text`, `context`, `document`, `detail`, `status`, `note`, `summary` or `message` (as for the label-like names) that is a `String` and is not shown, unless it is named there with why not.

## A member the node hosts (agency#77, #201)

`Me.guest = { member, org }` is present only when the viewer is a member the node hosts (a guest of it), and the app reads it as the web does (`guestOf`): **any `guest` that is not null counts**, whatever its shape, a field that is missing or not text is not read, and the viewer is still a guest: if the node says it in another shape, they must get a guest's screens and not the owner's tabs and refusals. A guest's `funding` is `[]` only because the field is required, and no funding area is drawn for them.

`Standing` (`loading`, `unknown`, `member`, `guest`) is what the desk's read of the account says (`DeskStore.standing`) and decides the screens offered (`AppTab.tabs(for:)`): a guest has **the desk and the devices**, and so has a viewer the node has not told yet (the owner's tabs appear once it has answered, as the web's menu does: a guest is not offered the owner's screens for a moment); anyone else has every screen, and a read that failed with nothing earlier to go by counts as anyone else, so that the screens show their own failures (an ended sign-in says nothing of who is asking and leaves the viewer not told). The router (`ShellRouter`) never opens a screen the viewer does not have: a banner or a tapped notification that leads to the participants, the overview or the results leads a guest to the desk, and a screen that is open when the node says the viewer is a guest closes. After a key reset the new session starts from the standing the old one had (the same node and the same account: `DeskStore(standing:)`), so an owner's open screen is not closed to the desk while the node is asked again; a failed read keeps it, and the node's next answer replaces it. A node that could not be read (`unknown`) offers every screen, as `member` does, so that each screen shows its own failure. The sign-in again does not read the owner's screens for a guest (they would be refused), and no owner screen is built for one.

## Words of the node the app does not know

A newer node may say a word an older app has never seen (`docs/compatibility.md`: "A new enum value in an answer"). Every enum the package decodes reads it as `unknown` and carries on: the rest of the answer still reads, and the new word is never one of the known ones, a success among them. `OpenWireEnum` does it for the enums of plain words; `DecisionState`, `WaitingOn`, `TeamSnapshot.Source` and `DeviceChangeResult.Outcome` decode themselves and keep the word. What the app does with an unknown word is the safe thing, and the screen says so where the owner could be misled:

- a request of an unknown kind is on the desk and counted, in a group of its own (「このアプリが知らない種類の依頼」), named 「依頼」; it is answered like any request when the node's `answerWith` names a kind of envelope the app knows, and when it does not, nothing is offered and the request says it cannot be answered here (`DeskItem.isAnswerableHere`, `DecisionEnvelope.Kind.unknown` is refused by `validate()` before anything is signed);
- a decision in an unknown state is listed without a colour that says it went well (「状態を読み取れません」); an unknown outcome of a device change is shown with the node's message and is not a success;
- an unknown kind of funding, usage window or blocked reason has a plain word (「ほかの資金源」, 「ほかの枠」, 「待機中」), and a participant who is not a human is listed with the agents;
- a source of a team's view the app does not know is shown as the node gave it, with no word on its age.

`OpenWireEnumsGuardTests` reads the package's sources and fails for a decoded enum that does not do this, unless it is named there with why it is not a word of a node's (the three it names are kept on the device by the app itself).

## What waits for the root key's signature (agency#381)

An org whose root key asks for its owner's presence holds a change someone else asked for (a new member, a new device) until the owner signs it on the root key's node with `agency root-sign`. The apps say it in two places, in the same words as the web's.

- **The desk.** `Me.rootChanges` (the owner only; absent when none waits) is one item below a started recovery: how many wait, a line for each (what it changes, the org's label, or its id when the account does not list the org, and how long ago it was asked), and the sentence that gives `agency root-sign`, which signs them together. Each change is worded by the app from its `kind` and fields (`addMember`: member, label; `addDevice`: member, label; `removeDevice`: member, device). The node's English `what` is said only for a kind the app does not know or a known kind that lacks a field, and a change with neither is left out. The command is the app's own constant, never the node's text, so no id goes into it. Nothing is drawn until `/api/me` has answered, and nothing when none waits; a failed read leaves what was shown, and the item goes when the node stops naming them.
- **The words of the push (iPhone).** The node writes the alert of a recovery and of a held change in English (`agency: { type: "recovery", org, startedAt?, finishesAt? }` and `{ type: "root", org, id, waiting }`). The notification service extension replaces its title and body, from those facts, with `PushNotice` (`AgencyKit`): in Japanese or English by the device's language, with the times of a recovery in the viewer's zone (`11月26日 18:30`, `Nov 26, 4:30 AM`) and a time that is not one left out; the org only when it is an identifier; the number of changes when more than one waits. The same words as the web's worker (`push-notice.js`). The node's own text, which names a member's or a device's label, is not shown. The Mac has no notification service extension, so its notice stays the node's English.
- **The push for it.** The node's push of the kind `root` (`agency: { type: "root", org, id }`, its title and body written by the node, sent to a token that asked for `root` or `device`) opens the desk of the home node that sent it, where the item above is; its `id` (the held change's handle) is not used.
- **A device approval the root's node holds.** The node answers `outcome: "pending"` to the change that approves a device. The request then says "Approved here; it takes effect once the root key's node signs it: run `agency root-sign` there." (in Japanese in the app, whatever `message` the node sent), with an hourglass and not the check mark of an add, and cannot be approved again until the request leaves the list. A request approved earlier (before the app was closed, or from another device) is held too, for as long as `Me.rootChanges` has an `addDevice` with that device's id; a read of it that fails leaves what was known. With several orgs, what an earlier org held stays said when a later one fails (`DeviceChangePartlyAnswered`), and the failure is said under it with the button still there. The node's `message` is said as it is only for an outcome the app does not know (`DeviceChangeResult.Outcome.unknown`), so that a new outcome neither makes the answer unreadable nor is shown as a success.

## The participants of a team's evaluation (agency#364)

A team's `evaluation` has, for the team's owner reading on their own node and when the team's runtime reports them, `participants` and `unattributedMerged` (`TeamEvaluation`): for each participant the seconds in the period at least one of their sessions was working, was waiting for a human's decision (a lower bound: a runtime sees only some of the waits) or was alive and neither (overlapping sessions count once), their cost, tokens, merged pull requests, and the cost per merged pull request. For anyone else the fields are absent, which is not the same as none, so they are optional and nothing is drawn without them (an empty list draws nothing either, as on the web).

Each team's evaluation shows them after its charts (`ParticipantsView`, the web's order): for each participant a bar of three parts (working, waiting, idle) by their share of the three, the three durations in words, the cost with the four kinds of token added up, the merged pull requests, and the cost per merged pull request (or 「マージなし」, never a $0); a participant with no session alive has no bar and says so; the pull requests no participant is named the author of are said when there are some. The words are the web's (`evaluation.participants`). The participants' `merged` and `unattributedMerged` add up to the summary's merged and reverts, which a test checks on the shared samples.

## Build

You need Xcode and [XcodeGen](https://github.com/yonaskolb/XcodeGen) (`brew install xcodegen`).

```sh
cd apple
xcodegen generate
xcodebuild -project Agency.xcodeproj -scheme Agency \
  -destination 'generic/platform=iOS' -configuration Release \
  CODE_SIGNING_ALLOWED=NO build
```

The generated `Agency.xcodeproj` and `App/Info.plist` are not committed. They derive entirely from `project.yml`, a regenerated project file produces merge conflicts, and the signing values must not leak into the repository.

Xcode puts build output in `~/Library/Developer/Xcode/DerivedData`. Delete the folder of this project when you are done, or pass `-derivedDataPath` to keep it somewhere you can remove.

Test the package, with no simulator and no Xcode project:

```sh
cd apple/AgencyKit && swift test
```

Continuous integration runs the same command on Linux. The app itself is not built in CI, because the repository has no macOS runner.

## Signing values

Copy `apple/Local.xcconfig.example` to `apple/Local.xcconfig` and set:

- `DEVELOPMENT_TEAM`: the Apple Developer team ID.
- `PRODUCT_BUNDLE_IDENTIFIER`: the bundle ID of the app record in App Store Connect.
- `AGENCY_ASSOCIATED_HOST`, `AGENCY_ASSOCIATED_HOST_2`: the host names (or `*.` wildcards) of the home nodes the owner uses. They go into the app's associated domains; a node on one of them signs in through a universal link, any other `https` node only through the app's own scheme, and only when that node's owner turned `access.allowSchemeSignIn` on. Leave the second one out when there is no second host.

`Local.xcconfig` is ignored by git. Without it the project builds with a placeholder bundle ID, which cannot be signed.

## Release in two commands

Two scripts in `apple/scripts` take the app from a bundle ID to a TestFlight build. Both read the App Store Connect API key from the environment and from a file outside the repository, and print none of it.

Once, by hand:

1. Create an App Store Connect API key (Users and Access, Integrations) with the App Manager role. Keep the `.p8` file outside the repository (the scripts refuse a key file inside it). Note the key ID and the issuer ID.
2. Fill in `apple/Local.xcconfig` (see "Signing values").
3. Create the app record in App Store Connect with that bundle ID. The API cannot create app records, so this one step is in the web page.

Then set the key where the scripts can see it. Do not put these in a file in the repository:

export ASC_KEY_ID=XXXXXXXXXX                           # its 10 character key ID
export ASC_ISSUER_ID=00000000-0000-0000-0000-000000000000
```

**`apple/scripts/register-bundle-id.sh`** registers the bundle ID from `Local.xcconfig` for iOS if the account does not have it, and enables the Push Notifications, Associated Domains and App Groups capabilities on it; it does the same for the widget extension and the notification service extension's bundle ID (the app's with `.widgets`), with App Groups. It signs the API token itself (ES256, valid for ten minutes) with `openssl`, and calls the API with `curl` and `jq`. It creates only what is missing, so it can be run again at any time, and it says what it did:

Enabled App Groups.
Registered bundle ID com.acme.agency.widgets.

```

The name of a new bundle ID is `Agency`, and of the widget extension's `Agency Widgets`; set `ASC_APP_NAME` and `ASC_WIDGET_NAME` to use others. The API cannot create the app group (`group.<bundle ID>`): make it once in the developer portal (Identifiers, App Groups), or let Xcode's automatic signing create it during the TestFlight build, which runs with the App Store Connect key.

**`apple/scripts/testflight.sh`** does everything for one build:

1. generates the Xcode project (`xcodegen generate`),
2. archives the Release configuration with a build number made from the current UTC time (`BUILD_NUMBER` overrides it; the number must be higher than the last one uploaded for this version),
3. exports with `ExportOptions.plist`, whose `destination` is `upload` and `method` is `app-store-connect`, so the export step sends the build to App Store Connect,
4. deletes `apple/build/` and this project's DerivedData folder, also when a step failed.

The build says which source it was made from (`AgencyBuildCommit` and `AgencyBuildDescribe` in its `Info.plist`: the commit, and `git describe` against the `apple-v` tags), and every upload that succeeded is appended to `apple/uploads.log` (not committed). See [releasing.md](releasing.md) for versions and tags.

Both scripts stop before doing anything, and list every problem at once, when `apple/Local.xcconfig` is missing or still holds the placeholders, a key setting is missing or malformed, or the key file is unreadable or inside the repository.

After processing (a few minutes), the build appears under TestFlight in App Store Connect. Add the owner as an internal tester. Internal testing needs no beta review.

To keep an `.ipa` instead of uploading, set `destination` to `export` in `ExportOptions.plist`; the script deletes `build/` at the end, so run the two `xcodebuild` steps from the script by hand and upload the `.ipa` with the Transporter app.

`MARKETING_VERSION` (the version the owner sees) is set in `project.yml`.

## Signing in with a passkey

The app signs in to Access in an `ASWebAuthenticationSession`. It runs in Safari's context, so passkeys and password managers work, and it needs no password prompt of its own. (A `WKWebView` could not run WebAuthn for the Access team domain, `<team>.cloudflareaccess.com`: iOS allows that only for a relying party that is one of the app's associated domains, and the file that says so would have to be served by Cloudflare.)

The token never travels in an address. The app asks for a code, and trades the code for the token over its own connection (`SignInExchange` in `apple/AgencyKit`; the node's side is "App sign-in" in `docs/protocol.md`):

1. When the desk has no Access token yet, or the session ended (the node answers with a redirect to Access's login), the app makes a `state` (256 random bits) and a `verifier` (256 random bits that stay in the app), and starts the session on `https://<node host>/app/handoff?state=<state>&challenge=<SHA-256 of the verifier>&via=<link or scheme>`. The first launch starts it by itself once.
2. Access signs the owner in and returns to the handoff route, which sits behind Access. The node keeps the token, makes a single-use code for it, and answers with a redirect to the callback with `#code=<code>&state=<state>`.
3. The callback is `https://<node host>/app/callback` (a universal link, when the build has an associated domain for the node's host) or `agency-signin://callback` (the app's own scheme, for any other node whose owner turned `allowSchemeSignIn` on; the node answers `400` otherwise). The app checks the scheme, host, path and port, that there is no query, that the fragment is exactly the code and its own `state`, and that the code is used once and within ten minutes. A callback that is not the sign-in's own is ignored and does not end it.
4. The app sends `POST /app/redeem` with the code and the verifier to the node it signed in to, and nowhere else. The node gives the token only for a code that is unused, young, and made for that verifier. The app keeps the token in the Keychain under that node's host.

Whether it can be used is decided by the build and by the node:

- The node must be on `https`. A node on a host the build has an associated domain for (`AGENCY_ASSOCIATED_HOST`, `AGENCY_ASSOCIATED_HOST_2`; each a host, or `*.example.com` for the hosts one label below it) signs in through a universal link, port 443 only. Any other `https` node signs in through the custom scheme only when its owner turned `access.allowSchemeSignIn` on (it is off by default: the node answers `via=scheme` with `400`, and the system sheet shows why). The scheme is delivered to the app that starts the session, whatever app that is. A node that is not on `https`, or that does not take part in the exchange, makes the screens say that the app cannot sign in to it.
- What the exchange does not stop: with `via=scheme`, any app on the device can run the whole flow itself (it makes its own `state` and `verifier`, starts the session, and receives the callback on the scheme). The verifier keeps an app that only listens for the callback from using a code it did not ask for; it does not keep an app from asking. What stands between is the owner's own sign-in on the Access page the system sheet shows. So the node refuses the scheme unless its owner turned `allowSchemeSignIn` on knowingly, and a node that must not be reachable this way keeps its host in the associated domains, where the callback is a universal link only this app receives.
- Leaving a home node forgets its token. The session in Safari is separate and is left alone.

What it needs:

- **The node:** the `/app/handoff`, `/app/callback` and `/app/redeem` routes and, for universal links, the association file, with the app identifier (`<team id>.<bundle id>`) in the node's configuration, and for a host that is not in the build's associated domains `allowSchemeSignIn` (see below on what it allows). A node that answers the scheme with `400` shows its reason in the system sheet; the app has no other way to tell it from one that does not take part.
- **Cloudflare Access:** a bypass policy for `/.well-known/apple-app-site-association`, because Apple's servers fetch the file without signing in, and for `/app/redeem`, which the app calls without Access (the code and the verifier are its credentials). The Access application must not bind its token to the browser, because the token is made in Safari and used by the app.
- **The build:** `AGENCY_ASSOCIATED_HOST` (and `AGENCY_ASSOCIATED_HOST_2`) in `Local.xcconfig`. The project's minimum iOS is 17.4, the first version with `ASWebAuthenticationSession` callbacks on an https address.

## Several home nodes

The device keeps a list of home nodes (`HomeNodeBook`, in `apple/AgencyKit`): the current one, the ones the owner added, and the other nodes the current node names for the owner (`/api/me` `homeNodes`). Settings shows it: the owner switches to a node, adds one by its address, or forgets one.

- **Switching** changes which node is current. Everything the app keeps for a node (its token, its device key, its drafts and its choices) is kept by the node's host, so switching moves no secret and the node left is signed in as it was when the owner comes back. What the old node put on the icon and on the widgets goes; the new node's desk is read and shown.
- **Forgetting** is for a node the owner added (a node the current node names comes back from it, and is not offered). After the owner confirms, it first tells the node to stop sending notifications to this device's push token (`DELETE /api/push/tokens/<token>`, while the sign-in still works), then takes the node off the list and removes its token, its device key, its drafts and its choices. When the node cannot be told (no sign-in there, no network, no answer in ten seconds), the screen says so and the owner chooses to forget anyway or not; a node that was not told keeps sending until the device is removed on its devices screen. The node's own list of devices keeps this device either way.
- Everything the app keeps for a node is keyed by its **host alone**, so forgetting removes it only when no other node on the device (the current one, an added one, one the current node names) has the same host with another scheme or port; the current node is never forgotten.
- **Leaving** the current node (the button at the end of settings) tells the node the same way, forgets the token, and returns to the address screen. The node stays on the list, so it can still be forgotten, and its key, drafts and choices stay for when the owner signs in again.
- The list is addresses and names only. The list of an earlier version (one address) is read as the current node and is replaced by the list on the first change; an earlier build then finds no address and asks for one.
- **A notification from another node.** Every push names the node that sent it (`agency.node`, an id the node works out from its address; `docs/protocol.md`, "The node names itself"). The app knows each node's id from what the node said in `/api/me` (`Me.nodeId`), and from its address until it has said (`NodeID`, pinned by `testdata/node-id.json`). A tap on a notification of the open node, or of a node that names none (an older node), opens it as before. A tap on one of another node on this device goes to that node (clearing the icon number and the widgets of the one left, as a switch by hand does) and opens the notification there once its shell is up (after a sign-in, when that has ended). Until the open node has said its own id (the first account read after an update), a tap whose id is none of the other nodes' waits for that read, so that a node known by a different address than its own is not taken for a stranger (once the read has finished, with an answer or without, a node that has still not said its id is not waited for, and such a tap is said not to be of this device); a tap that has waited more than a minute is dropped. A tap on one of a node this device does not have (forgotten, or never added) opens nothing of it and says so in one line, naming the org when the notification has one. This holds for every kind of push, a started recovery included.
- **The number on the icon is the sum over the nodes** (agency#117). A push's `badge` is its own node's count, so the app keeps each node's last count (`BadgeLedger`, a file in the app group's container, by the node's id) and shows the sum over the nodes this device has. The open node's count is recorded each time its desk says it changes, and the **notification service extension** (`AgencyNotificationService`, `apple/NotificationService`) records the count of the node whose alert arrives while the app is closed, and sets the icon to the sum before the alert is shown (`mutable-content` on the alert; the decision is `BadgeFromPush`, tested in the package). It uses no network and keeps no title, and when the push names no node, carries no count, or comes from a node this device does not have, it delivers the alert as it came. A node loses its count when it is left or forgotten.
  - **What stays imperfect, and how a wake narrows it:** a node's count changes when its own alert arrives or when it is opened, and also when a silent wake of that node arrives (the node names itself in it): the app then reads that node's desk in the background with that node's own sign-in, and records its true count (`WakeTarget`, `DeskWaitingCount`; the widgets are written only for the open node). A request answered elsewhere is therefore corrected at the node's next wake, which the node sends at most once in 15 minutes, and not before. A node that was left stays on the list but is not counted until it is opened again, so a late push of it does not put its count back. The Mac has no extension and no app group: its Dock badge is the open node's count.
- Widgets and the background refresh follow the current node only.

## Push notifications

The node sends a notification when a request starts waiting for the owner, when a device asks to be added, and when a decision of the owner's is refused, to the kinds each registered token wants. The app side:

1. **Permission.** The app does not ask on the first launch. After the owner has signed in (the first time the desk has loaded, which only happens past Access), it shows a one-line explanation and then the system prompt, which asks for alerts, sounds, and the badge on the app icon together (iOS does not ask again after the first answer, so the badge is part of the first request). "Not now" asks again after a week. A refusal in the system prompt is never asked again; the owner can change it in Settings. `PushPromptPolicy` holds the rule.
2. **Token.** When permission is granted, the app registers for remote notifications on every launch, because the token can change.
3. **Registration.** The app registers the token with the node itself (`POST /api/push/tokens`, with the write token and the Access token) once the desk has loaded. `token` is the APNs device token in lowercase hex, `environment` is `sandbox` or `production`, `label` is the device model (`iPhone`), never the device's name, and `events` is the kinds the owner chose in the settings (`request`, `device`, `decision`; every kind starts on). A change in the settings registers again, which the node takes as an update. A node that predates kinds answers 400 to `events` (it refuses a field it does not know) and sends requests only: the app registers again without `events`, and the settings say that this home node sends requests only.

   **The registration names its device** (agency#448): when the node lists `pushDevice` in the `capabilities` of `GET /api/about` and this phone is in the node's list of devices, the registration carries `device`, this phone's id there, and the node drops the registration when that device is removed (a removal from the Devices screen, agency#443, then also stops this phone's notices). This phone's id is that of its row in the list (`DevicesStore.thisDeviceID`): ids are made from the key, so the same key has the same id in every org and there is one row for it. A phone that is not in the list is **not registered at all** on such a node (the node refuses a device that is not the account's, and an unnamed registration stays until it is removed by hand, which would bring the notices of a removed phone back: a new key made after the phone's own removal is registered when it is added). A node that does not list `pushDevice` is sent none (any other answers 400 for the field), and what the node says of itself is waited for: a failure to read it is tried again at the next registration, and a node with no such route (404) is one with no capabilities. The registration is made again when the phone appears in the list. A 400 for a registration that names its device is **never** made again without it, since one that went through would not be tied to the device: the list of devices is read again instead. A phone that was named and then removed keeps the device it was registered with, and is not registered again without it.
4. **Tap.** A request's notification carries `agency: { org, team, request }`: tapping it opens that request on the desk (`<org>:<team>:<request>` is the id of a desk item). A device's carries `agency: { type: "device" }` and opens the devices tab; a refused decision's carries `agency: { type: "decision", org, team, id }` and opens the desk. Values that are not plain identifiers (letters, digits, `.`, `_`, `-`), a type the app does not know, and a payload without `agency` give no link, and the app just opens.
5. **Wording.** The alert of a device or a refused decision is worded by the app, from `loc-key` and `loc-args`: `Shared/ja.lproj/Localizable.strings` and `Shared/en.lproj/Localizable.strings` hold the five strings the node names (`PUSH_DEVICE_WAITING`, `PUSH_DEVICE_WAITING_NO_LABEL`, `PUSH_DECISION_REFUSED`, `PUSH_DECISION_REFUSED_NO_TITLE`, `PUSH_REQUEST_WAITING_HIDDEN`), and a test checks that both languages have exactly those and the number of arguments the node sends. The development language is Japanese.

6. **Badge.** The app icon shows how many requests wait for the owner. The node puts the count in `aps.badge` of each push (an integer: the requests addressed to the owner across all orgs and teams, counting the one the push is about), and a push that arrives while the app is open sets the badge too. While the app is open, the desk keeps the number current (the sum of `mine` over the teams it could read), so deciding a request lowers the badge without another push. Changing the home node sets the badge to 0. While the app is closed, the badge can be out of date if a request is decided somewhere else, until the next push or until the app is opened.

`aps-environment` is `development` in Debug builds and `production` in Release builds (`APS_ENVIRONMENT` in `project.yml`). The same value goes to `Info.plist` as `AgencyAPNsEnvironment`, which is how the app tells the node which APNs host a token belongs to. TestFlight and App Store builds are Release, so they register as `production`; a build run from Xcode on a device registers as `sandbox`.

What has to be in place outside the repository:

- The App ID for the bundle ID has the Push Notifications capability. With automatic signing and the API key, `-allowProvisioningUpdates` normally enables it when the entitlement is present; check it on the first archive.
- The node has an APNs key (a `.p8` from the developer account), its key ID, the team ID, and the same bundle ID as the topic. These are credentials: keep them out of the repository.

## The widgets

A widget shows what waits on the owner: the number of requests that are the viewer's to decide (the desk tab's number) and the first three of them, each with its team. The home screen has a small and a medium widget; the lock screen has a circular one (the number), a rectangular one (the number and the first request) and an inline one ("決めること N 件"). A tap opens the desk at the first request; on the medium widget each request opens its own.

- **The data.** The app writes one small file, `widget.json`, into the app group's container after each desk read, and removes it when the home node is left. It holds a version, when it was written, the home node's host, the count, and for each of the first three requests its org, team and request ids, its kind, its title (cut to 80 characters) and its team's label: no people, no bodies, no options, no token and no key. The widget never holds the Access token or a device key. The file is readable after the first unlock (the widget reads it while the phone is locked) and written whole or not at all; a file of another version, or one that is not a snapshot or is far too large, is ignored.
- **Privacy.** Titles are `privacySensitive()`: on the lock screen the system hides them and the count stays.
- **Titles off.** A home-screen widget shows titles to whoever sees the phone (and in StandBy, while it is locked). The owner can turn "ウィジェットにタイトルを表示" off in the settings (on by default, kept per home node on this device): the file is then written without titles and team labels, so only the count and the kind of each request are on the device at all, and the widget shows those. A node that sets `hideTitles` (see `docs/protocol.md`, Push notifications) is to say so in its answer to `GET /api/me` (`hidesTitles`; the node does not send it yet, agency#272, and the app counts a missing field as `false`); the file is then written without titles whatever the switch says. The switch can only hide more, never show what the node hides, and the settings row says that the node hides them.
- **While the app is closed** (agency#261). The node wakes the app with a push that has only `content-available` (and a request's alert carries it too), at most once in 15 minutes (docs/protocol.md, "Waking the app to read the desk"). The app declares the `remote-notification` background mode, and `AppDelegate.application(_:didReceiveRemoteNotification:)` reads the desk with no window and no session (`BackgroundDeskRefresh`: the saved home node, the Access token from the Keychain, which is readable after the first unlock, one read of the account and every team without waiting for a team that is not ready, then the same file and the same rules about titles). It does nothing when the app is in front, and not more than once a minute; it stops after 25 seconds, a little before the system's limit. A run that cannot read the whole desk (the sign-in ended, a team did not answer) writes nothing, because a number made of the teams that answered would be wrong; the widget keeps its file and says how old it is. iOS may throttle or skip a background push: the widget is then as late as it was before.
- **When the file is removed.** On leaving the home node, and when the device's key is reset (a reset means this device is no longer trusted with that home node). An ended sign-in keeps it: the three-hour mark on the widget covers that.
- **`AgencyWidget`** is a package target that depends only on `AgencyKit`: the snapshot, its file store, the link, the words and the SwiftUI views. A widget extension has a small memory limit, so it must not link `AgencyAPI`, `AgencyProtocol` or swift-crypto. `AgencyModel` depends on it and holds the builder that works the snapshot out of the desk (`WidgetSnapshotBuilder`). The views are plain SwiftUI (no WidgetKit names), so they are drawn offscreen at the widgets' real sizes in the tests, and the tests fail when a widget would need more height than it has.
- **The tap.** The widget's URL is `agency://request?org=..&team=..&request=..` (`WidgetLink`). It only says where to go, and the app accepts it only when all three values look like identifiers (`RequestLink`). No URL scheme is registered in `Info.plist`: Apple's documentation says the system activates the containing app and passes a widget's URL to `onOpenURL`, and says nothing of registering it, so no other app or web page can open the app with it. This could not be tried on a device from here: if a tap only opens the app, the fallback is one `CFBundleURLTypes` entry for `agency`.
- **Refresh.** The widget shows the file as it is and says how old it is once it is older than three hours; the app asks the system to reload the widgets after it writes. The system budgets reloads, so the widget can be later than the app. A silent push from the node, with the remote-notification background mode, would refresh it while the app is closed; that is not built (agency#207).
- **The notification service extension.** `project.yml` has a second extension, `AgencyNotificationService` (`apple/NotificationService`), embedded in the app, with the bundle ID `$(inherited).notifications` and the same app group; it links only `AgencyKit` (the memory limit of an extension is small). The account needs its bundle ID registered with App Groups (`apple/scripts/register-bundle-id.sh` does it) and the group ticked on it in the developer portal, which the API cannot do.
- **The targets.** `project.yml` has the extension `AgencyWidgets` (`apple/Widgets`: the widget bundle, the timeline provider that reads the file, the entitlements and an `Info.plist` that is generated). Its bundle ID is the app's with `.widgets` (`$(inherited).widgets`, so it follows `PRODUCT_BUNDLE_IDENTIFIER` in `Local.xcconfig`), and it is embedded in the app. Both carry the app group `group.<the app's bundle ID>` in their entitlements (the extension's is `group.$(PRODUCT_BUNDLE_IDENTIFIER:base)`, the build setting with its last suffix removed), and the same name in `Info.plist` as `AgencyAppGroup`, which the code reads: the extension links only `AgencyKit` and `AgencyWidget`. The app writes the file (`WidgetPublisher` in `AgencyModel`, with the app group's container and WidgetKit behind a small protocol; `ShellModel` calls it after the desk read and `ShellChrome` on each change of the desk's requests, so it does not depend on which screen is open; a write that would say the same as the last is skipped, because the system budgets reloads) and removes it when the home node is left, after which that publisher writes nothing again (a read that was under way cannot bring the old desk back); a tap's URL goes to `onOpenURL` in `AgencyApp`, which opens the request like a tapped notification.
- **The Mac.** The same extension can be built for macOS 14 (WidgetKit runs there), reading the same snapshot from the Mac app's group container; `AgencyWidget` has no iOS-only code except the file protection class of the written file.

## What is new

The app and the web client use one definition of "what is new" (agency#167), pinned by `testdata/notifications.json`. A client keeps the last answer it read for each team, for the list of devices that asked to be added, and for the decision log. An event is the difference between that answer and the next one; the first answer of each is a baseline and makes no event, and a part that could not be read keeps its last answer, so the read after a failure is not "everything is new". The events are a request that now waits on the viewer (`mine`), a participant who now waits on the viewer, a work item that is newly blocked, a device that asks to be added (other than this phone's own key, and only when this phone can approve one), and a decision that changed state (a success this phone sent is not news, a failure or a queued one is). Each has a stable key (`request:org/team/id`, `participant:org/team/id`, `blocked:org/team/ref`, `device:<key>`, `decision:id:state`), and the events of one reading come ordered by kind and then by key. `EventEngine` in `AgencyModel` is the Swift side; the web client's engine reads the same file and has to make the same events. The counts (the badge, the mark on the devices tab) are not events: they are the current number.

### What the owner chooses

The settings sheet (the gear on the desk) has two sections, for each home node: which kinds of news show a banner while the app is open (all five), and which kinds are sent as a notification while it is closed (request, device, refused decision). Every kind starts on. The choices are kept in the app's defaults per home node (`agency.notifications.<host>`).

### The news, as banners

`NewsStore` (`AgencyModel`) turns the events of that definition into what the app shows while it is open. Each `poll()` reads the account, every team (through the shared cache), the devices and the decision log, gives the reading to `EventEngine`, and makes at most three banners, one for each kind of event: worded for one event ("<team>: 「<title>」があなたを待っています") or for several ("3 件の依頼があなたを待っています"), and leading somewhere (a request opens on the desk, a device to the devices screen, a participant or a blocked item to the people screen). A kind the owner turned off, or one the visible screen already shows (the devices while the devices screen is open), makes no banner, and its events are still taken so they are not announced later. A decision this phone sent is remembered for the session (`SentDecisions`), so its success is not news and its failure is.

The shell polls the news while the app is in front: once when it comes to the front (which is also when events that piled up while it was away arrive, together, in order) and every 30 seconds after that. The banners (`NewsBannerStack`) sit at the top, last 7 seconds, and have a cross; a long text wraps to three lines and the full text is on the screen the banner leads to. The first reading after launch is a baseline, so opening the app announces nothing that was already there.

## Protocol code in Swift

The native screens of agency#77 build and sign decisions in Swift. The `AgencyProtocol` module of `apple/AgencyKit` holds that code: canonical JSON, the signed text (`agency/v1/<kind>`, a newline, the canonical JSON), the decision envelope with the shape checks the node makes, and the key fingerprint with the pairing code and device id. Its tests read `testdata/vectors.json`, which the Rust side produces: each body is built in Swift and has to encode to the vector's canonical JSON, and the vector's Ed25519 signatures have to verify over the bytes Swift made. A change of the protocol that the Swift code does not follow fails those tests.

The `AgencyAPI` module is the client of the home node's Client API (`NodeClient`, with the transport behind a protocol) and the wire types it reads (`Me`, `TeamSnapshot` with its `TeamView`, `DecisionLog`, `DecisionResult`, `Session`). Each type decodes the node's real answer in `testdata/client/`, which the Rust tests record and fail on when it changes, so a field the node renames or drops fails a Swift test before it reaches a screen. A value the client does not know (a new request kind, a new decision state) fails to decode instead of being read as another. The client's rules:

- Every request carries the Access token as `cf-access-token`. A redirect is Access ending the session: the client throws `sessionExpired` and never follows it.
- A write also carries the write token from `GET /api/session`, fetched on first use and once more after a 403 that says the token is missing or wrong (it changes when the node restarts). Any other refusal, and a second one, is the answer and is not sent again.
- The same call gives the node's time. A signed envelope's `at` comes from `nodeNow()`, because the node refuses an envelope more than five minutes ahead of its own clock.

The `AgencyModel` module is what the screens show, ported from the web client with its test cases so the phone makes the same rules: the desk's pile (groups proposal, question, pending decision, and requests for someone else; the request that stops more people first; then the oldest), presence and the one-line summary, and the owner's replies. Whose a request is, is the node's call (`mine`); the model never works it out from `to`.

A reply is one of three things. **Choosing** an option decides the request, with an optional note. **Commenting** is text with no option on a request that has options: the team gets the message and nothing is decided, and the screen says so. **Answering** is words on a request that has no options. The title and the chosen option's label that go to the decision log are cut to 200 characters (Unicode scalars, as the node counts), because the node refuses a longer note.

The `AgencyUI` module holds the SwiftUI screens (iOS and macOS, nothing UIKit-only), and the words are in `AgencyModel` (`Ja`, taken from the web client's Japanese where it has the text), so they are tested on every platform. `DeskStore` is the desk's state: it reads through `NodeClient`, keeps drafts per request across launches, and sends a prepared reply through a sender that signs it. `ReplyControls` decides what can be pressed, so the views only draw it. The rules of the layout come from the owner: no screen scrolls sideways, a long title or id wraps or is cut with the full text one tap away, and nothing explains a keyboard.

The Linux CI job does not build `AgencyUI`. A change to it is checked on a Mac before it is merged: `xcodebuild -scheme AgencyUI -destination 'generic/platform=iOS' CODE_SIGNING_ALLOWED=NO build` in `apple/AgencyKit`, and `swift test`, whose rendering tests draw each screen at a phone's width with `ImageRenderer` (offscreen, nothing launches) and fail when anything is wider than the screen. Set `AGENCY_SNAPSHOT_DIR` to a folder outside the repository to keep the PNGs. They are made from fixtures only.

Two rules in the encoder come from the protocol and are easy to break. Keys sort by their UTF-8 bytes, which is not Swift's string order and not UTF-16 order. Text is never normalized: Swift treats `é` and `e` plus U+0301 as the same string, but they are different signed bytes, so objects keep their members as a list and compare bytes.
