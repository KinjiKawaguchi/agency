# Agency protocol between nodes (v1)

Agency runs organizations in which AI agents and people work together, across many machines.
There is no central service.
The only central thing is authority (the key of the person who decides for the org); the data is split across machines.

## Units and writers

| Kind | Unit | Writer | Where it lives |
|---|---|---|---|
| Execution (activity, requests, decisions, board) | Team (one harness) | The node the harness runs on | The team's node |
| Governance (departments, members, where teams run, revoked keys) | Org | The org's root key (the person who decides) | Copied to the nodes of the org's teams and of its members |
| Account (key, memberships) | Account | That account's human | Its home node |

Every piece of data has exactly one writer.
Other nodes only keep replicas and never change them.
To change something, send a signed envelope to its writer.

## Identifiers

- Ids of accounts, orgs, teams, departments, and members: `[a-z0-9][a-z0-9-]{0,39}`
- Envelope id: 16 random bytes as hex (32 characters)
- Time: RFC 3339 in UTC (`2026-11-24T12:00:00Z`)

## Keys and signatures

- Root and account keys are Ed25519; a definition that lists any other kind is refused. A device key is Ed25519 or P-256, so a phone can keep it in hardware that only does P-256.
- An Ed25519 public key is written as its 32 bytes in standard base64 with `=` padding. A P-256 public key is written as `p256:` and its 65-byte uncompressed point (`0x04`, x, y) in standard base64 with `=` padding. No other form is read (not the compressed point), so a key has one text, one fingerprint, and one device id.
- An Ed25519 signature is its 64 bytes in standard base64. A P-256 signature is ECDSA with SHA-256 over the signed text, written as 64 bytes (`r` then `s`, 32 bytes each) in standard base64; either `s` is accepted (replay protection keys on the envelope id, not on the signature).
- Every node must understand P-256 keys before a person adds a P-256 device: a node that does not refuses the org versions that list one.
- Three kinds of key, each limited to what it may sign:
  - The root key, held by the root's node, signs org definition versions. Each org has a root key of its own, apart from the node's account key: the account key signs things the node does by itself, and the root key only versions, which a person makes. The root's node reads it only to sign, and may ask for its owner's presence first. An org made before root keys were kept apart has the account key as its root until it is rotated.
  - An account key, held by the account's home node, signs reads, join requests, and the account's first device in an org. It never signs a decision.
  - A device key, held by a client (a browser, a phone, or the CLI) and never by a node, signs decisions and changes to its member's devices.
- Fingerprint: the first 16 bytes of the SHA-256 of the public key's bytes (the 32 bytes of an Ed25519 key, the 65-byte point of a P-256 key, never the text), as hex (32 characters). Invite links carry it, so the invited node can check that the org's root key is genuine.
- The signed text is a kind line followed by canonical JSON: `agency/v1/<kind>\n` and then the body's canonical JSON. The kinds are `envelope`, `org`, `join`, `read`, and `device`. A signed read also has a text that names the node it is made for, under its own kind line, `agency/v2/read\n` (see "Signed reads"). Because of the kind line, a signature for one kind cannot be reused for another.
- Canonical JSON: object keys sorted by bytes, no whitespace, strings escaped as standard JSON, integers only, and fields whose value is null left out.
- A signed document: `{ "body": <body>, "signer": <id>, "signature": <base64> }`. `signer` is an account id, or, for a document signed with a device key, that device's id.

## Org definition (kind `org`)

```json
{
  "org": "acme", "label": "Acme", "version": 3, "prev": "<fingerprint of the previous version>",
  "root": { "account": "alice", "publicKey": "..." },
  "departments": [{ "id": "dev", "label": "Development", "parent": null, "head": "owner" }],
  "people": [{ "id": "owner", "label": "Alice", "account": "alice", "publicKey": "...", "department": "dev", "role": "member",
              "devices": [{ "id": "laptop", "label": "Laptop", "publicKey": "...", "addedAt": "2026-11-24T12:00:00Z" }] }],
  "teams": [{ "id": "app", "label": "app", "department": "dev", "node": "https://alice.example",
              "plan": { "allocation": { "newFeature": 40, "improvement": 20, "maintenance": 20, "debt": 15, "incident": 5 }, "weeklyBudgetUsd": 500,
                        "aims": [{ "epic": "app#10", "kpi": "activation" }] } }],
  "kpis": [{ "id": "revenue", "label": "Revenue", "kind": "business", "unit": "money", "currency": "JPY", "goodWhen": "higher" },
           { "id": "activation", "label": "Activation", "kind": "product", "unit": "percent", "goodWhen": "higher" }],
  "seats": [{ "id": "carol", "label": "Carol (finance)", "department": "dev",
              "askAbout": ["invoices", "budget approval"], "relays": ["owner"] }],
  "externals": [{ "id": "erin", "label": "Erin (outside counsel)",
                  "askAbout": ["contract review", "legal checks"], "relays": ["owner"] }],
  "revoked": ["<revoked public key>"],
  "at": "2026-11-24T12:00:00Z"
}
```

- Only the root key (`root`) can sign it. `signer` is `root.account`.
- Versions start at 1 and grow by 1. `prev` is the hex SHA-256 (64 characters) of the canonical JSON of the previous signed version. Version 1 has no `prev`.
- **The history.** A node keeps every version it took, and `agency audit --org <org> [--since <time>] [--json]` lists them oldest first. For each kept version it gives when it was signed; whether its signature is valid for the root key or the recovery key of the version just before it (of its own root, for version 1), and by which key's fingerprint, or is invalid, or could not be checked because the version just before is not kept here (the missing versions may have moved the root); whether its `prev` is the digest of the version just before it (one that is not is a fork of the history); and every change it made in words (the words of the presence prompt, none left out), counted from the last version before it that the node keeps (said when that is not the one just before). A version the node does not keep is listed as not kept. `--json` writes one object per version (`version`, `at`, `signature`: `valid`, `invalid` or `notChecked`, `signedBy`, `follows`, `comparedWith`, `changes`, `isKept`). The Client API serves the same entries to the node's owner (`GET /api/orgs/<org>/history`, see "Client API"), worked out by the same function, so the command and the route never disagree; the types are `HistoryEntry` and `OrgHistory` in `agency-proto`, and the shared sample is `testdata/history.sample.json`.
- A node accepts only the next version of the one it has: the version is one higher, `prev` is the current version's fingerprint, and it is signed by the current root key.
- Rotation: a version that names a new root (`root.publicKey`) is signed by the current, old, root key; every later version is signed by the new one, so the old key signs nothing once the rotation is accepted. A node that accepts it moves the trusted fingerprint it keeps for the org to the new key. The root's node rotates with `agency root-rotate --org <org>`, which makes the new key and forgets the old one once the version is published.
- What an old root key can still do: a node that has not yet taken the version naming the new root still treats the old key as the root, so a stolen old key can sign a different version in its place and that node would take it (a fork). A node that took the rotation refuses anything the old key signs, as it refuses any signature that is not its copy's root's, and a node takes only one version of each number. Rotate as soon as a root key may be exposed, and let every node take the rotation promptly (`agency sync`, or the next read).
- Commands: `agency root-recovery --org <org>` (on the root's node) makes a recovery key, shows its 24 words once (the BIP-39 English list, whose last word carries a checksum), has the owner type three of them back, and signs the version that names it; the node keeps nothing of it. `--replace` asks for the current words and starts replacing them with new ones. `--same-words-as <other org>` asks for the other org's words and, if they are its recovery key, names the same key here: one set of words then starts a recovery of either org, each with its own wait. `agency root-recover --org <org>` asks for the words and starts a recovery to a new root key made on this node; with `--finish`, it finishes the recovery that waits once this node has held it for the wait, and only on the node that made the new root key (the one where the start ran). A root key made for a start that is then cancelled is forgotten. `agency root-cancel-recovery --org <org>` (on the root's node) signs the next version, which cancels it. The words are read from the terminal without being shown (or from a pipe), never from an argument, and new words are shown on the terminal's alternate screen, which leaves no scrollback. While a recovery waits, `agency status` says so on its own line, and the node writes one line to its log when it first sees it, so a node with no device registered still says it.
- Recovery key: `root.recovery`, optional and left out when absent, names a second Ed25519 key that no machine keeps; the owner keeps it only as written words. It answers a lost root key, and words that may have been seen. Its capability is `orgRecovery`, so a root writes it only after every node it can name lists that capability. A recovery key is never the root key or an account key, and the new root key a start names is never an account key: a key a node keeps would defeat it (`validate` refuses it). What each key may sign, checked by `verify_successor` on every node:
  - The root key may change anything except `root.recovery`, which it may only set while there is none, and it never sets `root.pending`. A stolen root key therefore cannot remove or replace the recovery key.
  - The recovery key signs a **start**: a version whose only change is setting `root.pending` to `{ publicKey?, recovery? }` (at least one), the new root key, the new recovery key, or both. Nothing moves yet.
  - After the start, the recovery key signs a **finish**: a version whose only change is applying `pending` to `root.publicKey` and `root.recovery` and clearing it. A node takes a finish only when `RECOVERY_WAIT_SECONDS` (259 200, 72 hours) have passed since **it** took the start, by its own clock, which it notes when it takes the start. The wait is never counted from a signed time, because whoever signs a version chooses its `at`.
  - Any version the root key signs after a start clears `pending`, so it cancels the recovery: the root's node clears it on every version it signs, and the finish then has no number left.
  - A node that asked the root's node for a change (a join, a device change) takes only a root-signed version from the answer; a recovery reaches it only through `receive`, where the wait is counted.
- What recovery does not answer: the cancel is a veto for whoever holds the root key, so a recovery cannot take an org back from a stolen root key; the owner answers that with `agency root-rotate` from their own copy, at once. A cancel signed after some node already took the finish leaves that node with another version of the same number (a fork): it refuses the cancel, and the owner sees the fork. The owner should therefore cancel well before the time the start's notice gives.
- A node that is more than one version behind (it was offline, or reads rarely) takes the versions in between first, in order, from the node it reads the definition from (`GET /fed/v1/orgs/<org>/versions?after=<n>`), checking each as above. It does so when a read of the definition shows a newer version, and when the root's node answers a device change with one. Every node keeps the versions it accepted, so the root's node can serve all of them.
- Membership: an account listed in `people` whose `publicKey` is not in `revoked` (a hosted member, which has none, is a member while it is listed).
- **Removing a member:** `agency member-remove --org <org> --member <id>` on the root's node signs a version without the person, with the keys of their devices added to `revoked`, so that no device of theirs signs again under any member's name. It is refused for the root's own account (403), for an id that is no member (404), and while something still names the member (409, naming each): a seat or an external party it answers for, a department it heads, or a team on the root's node that it owns or that its `people` names, by the member's id or a seat it took (`formerly`). Teams on other nodes are named in those nodes' configuration, which the root's node does not see: a request there for the removed member waits for no one until that team's `people` is changed. From the version on, every node of the org refuses the person's signed reads and envelopes as a stranger's. The root's node drops the sign-in record and push registrations it kept for a hosted member. The root's node does not know which node a member runs, so it does not tell that node: the node's reads of the org's teams are refused from then on, and it shows them as failing. A seat the member had taken is not given back.
- A **hosted member** (`people[].hostedBy: "root"`, capability `hostedMembers`) has no node of its own: the root's node hosts it, and its clients use that node's Client API. It has **no account key**, so `publicKey` is left out, and only then; its `account` is its member id; it has at least one device, its only way to act; and it is never the root's account. It never signs a read or a join request: a read signed as it is refused like a stranger's (404), whatever key signed it. Its devices sign its decisions and device changes, as for every member. Every other member has a `publicKey`. Both fields are left out when absent, so versions signed before hosted members existed keep their canonical JSON and signatures.
- `devices` is left out when it is empty, so versions signed before devices existed keep their canonical JSON and signatures. Device ids are unique per member. A device key appears once in the whole definition, is never an account key or the root key (nodes hold those), and is never in `revoked`.
- Departments form a tree: a department's `parent` is another department of the org (or absent at the top), following parents never leads back to the department, and `head` is a member's `id`. A member's and a team's `department` is one of the org's departments. The root's node changes them with `agency dept-add`, `dept-set`, `dept-remove`, and `team-dept` (and `team-add --department`), each a new version.
- `teams[].plan` is what the org intends for a team, and is absent when it states nothing. `allocation` is the percent of the team's effort for each kind of work (`newFeature`, `improvement`, `maintenance`, `debt`, `incident`), five non-negative integers that add up to 100. `weeklyBudgetUsd` is the weekly spend the org intends, in whole US dollars, estimated at API prices like `TokenUsage.costUsd`; it is an integer because the definition is signed as canonical JSON. A plan has both. The root's node sets it with `agency team-plan` (`--none` clears it). A node that does not know `plan` refuses the versions that carry one, so every node of the org must understand it before the root sets one. Every node of the org must understand `plan` before the root sets the first one: a node that does not refuses the version that holds it (an unknown field) and stays on the version before it, since a node takes the versions in order, like with P-256 keys above.
- `seats[]` are places in the org that no one has taken yet (see Seat in the glossary), and `externals[]` are people the org works with who never take a seat (External party). Both are left out when empty, so a version signed before they existed keeps its bytes, and each has a capability (`orgSeats`, `orgExternals`: see compatibility.md), so the root writes one only once every node of the org lists it.
  - A seat has an `id`, a `label`, an optional `department` of the org, `askAbout` (what to ask it about: at most 20 texts of 1 to 200 characters, no control characters) and `relays`. An external party has the same, with a `relays` that is required. **Neither is a member:** it has no account, key, or device, so no rule that keys on `people[]` (membership, signed reads, devices, envelopes) can reach it, and it never decides. It holds a label and what to ask about only, never an address, an email, or a phone number: a seat or external party with a field this list does not name is refused. A label or an `askAbout` text this node writes now may not hold a character of `is_hidden_char` (see "Signing" under the held root changes); what an earlier version already had stays.
  - `relays` are the members who may answer for it, in order of preference (the protocol's name for them; in words, they *answer for* it). Each is a member, named once, at most 10; a seat never answers for anyone; an external party needs at least one; a seat with none falls to the team's owner. They address requests as "Requests" says.
  - An `id` is used once among `people[]`, the seats they took (`people[].formerly`), `seats[]`, and `externals[]`, so that it survives a seat being taken. A department that still holds a seat is not removed. An org has at most 200 seats and 200 external parties. The definition's own check refuses a version that breaks one of these, and names the id.
  - **Taking a seat:** a seat that someone takes leaves `seats[]`, and the member has `formerly` (the ids of the seats they took, at most 10), their `department` is the seat's, and `askAbout` (what to ask them about, the same limits as a seat's) is what the seat said. Both are left out when empty and have the capability `orgSeats` (a seat in the org means every node of it lists the capability already). A request addressed to the seat's id is the member's own from then on (see "Requests"), not an answer for anyone. A member's `formerly` can also grow by the root's choice, for a member who joined before (`agency seat-merge`).
  - The root's node writes them with `agency seat-add`, `seat-set`, `seat-remove`, `seat-merge --seat <seat> --into <member>`, `external-add`, `external-set`, and `external-remove` (`--answered-by <member>`, repeated, for `relays`); a `set` changes only the flags it is given. `agency status` lists them.
- `kpis[]` is what the org measures, and `teams[].plan.aims[]` what a team's plan aims at: labels and ids only, **never a number**, and no target figure either. The numbers of the business and the product are business data: they stay on the owner's node (see "Outcomes" in the glossary) and are not in the definition, which every node copies. A KPI is `{ id, label, kind, unit, goodWhen }`: `id` an id unique in the org, `label` 1 to 80 characters, `kind` `business` or `product`, `unit` one of `money`, `percent`, `count`, `ratio`, and `seconds` (a duration), `goodWhen` `higher` or `lower`. A `money` KPI has `currency` beside `unit`, an ISO 4217 code of three uppercase letters (`JPY`); money is never converted, so the org measures in the currency it reports in; no other unit has a `currency`. An aim is `{ epic, kpi }`: `epic` an item reference (1 to 200 characters, no control characters; the glossary's "Item reference"), `kpi` the id of a KPI the definition lists. At most 100 KPIs per org and 50 aims per team. An aim names a KPI the definition lists and is not repeated, so removing a KPI is refused while an aim names it. A team that states aims has a plan (an allocation and a weekly budget), since the aims are part of it; setting the plan again keeps its aims, and clearing it clears them. `kpis` and `aims` are left out when empty, so versions signed before they existed keep their canonical JSON and signatures. The root's node changes them with `agency kpi-add`, `kpi-set`, `kpi-remove`, `plan-aim`, and `plan-unaim`, each a new version.
- Every node must understand `kpis` and `aims` before the root adds the first: a node that does not refuses the version that holds one (an unknown field), and stays on the version before it, like with P-256 keys above.
- A team's `label` is changed with `agency team-set`, and a team leaves the definition with `agency team-remove`, each a new version written by the root's node. A node refuses `team-remove` for a team that is still in its own configuration: it would be left running outside its org.
- A node serves a team only while the team is in its own configuration **and** in the org's definition it holds. After the version that removes a team, its node answers reads and envelopes for it like for a team it does not run, until its owner takes it out of the configuration (`agency status` says so, and so does the start of `serve`). That version is queued for the removed team's node as well as for the nodes of the teams that remain, and a node that takes it deletes its replica of the removed team's view.
- `teams[].node` is the origin where other nodes reach a team. The node that runs a team knows it from its own configuration, not from this field, so a team keeps running and being served if the field still names an old origin of its node. That node reports the mismatch. The root's node fixes it with a new version that changes only that team's `node` (`agency team-move`).
- `role`: `member` (reads and answers) or `answerer` (only answers). Either decides only the requests addressed to them (see "Requests"). An answerer also reads only those: a team's node serves an answerer a TeamView with just the requests addressed to it, and no people, work items, or epics, and does not serve it token usage (403).

## The directory for agents

An org's agents must know whom to ask for what: this thing goes to this member, that one to a seat, a legal check to an outside party. A team's runtime knows the people of its team only by its own names (see "Requests"), and the org definition reaches it no other way, so a team's harness reads the directory from **its own node**:

```
agency directory --org <org> [--json]
```

It is local and read-only, and answers only for an org the node's account belongs to. `--json` prints the `Directory`:

```
Directory         { org, departments: DirectoryDepartment[], members: DirectoryMember[], seats: DirectoryParty[], externals: DirectoryParty[] }
DirectoryMember   { id, label, department?, role: "member" | "answerer", askAbout: string[], runtimeNames: RuntimeNames[] }
DirectoryParty    { id, label, department?, askAbout: string[], answeredBy: Id[], runtimeNames: RuntimeNames[] }
RuntimeNames      { team, names: string[] }
```

- The members, the seats, and the external parties are in the order of the definition. `askAbout` is what to ask a seat or an external party about, in the org's own words, and `answeredBy` the members who answer for them in order of preference (for a seat with none, the team's owner does; for an external party there is always one). A member has an `askAbout` only when they took a seat (it is what the seat said, `people[].askAbout`), and an empty one otherwise.
- `runtimeNames` is the names the **teams this node runs** know the addressee by: `owner` for a team's owner, and each key of the team's `people` that maps to its id, or, for a member who took a seat, to the id of that seat. A request whose `to` is one of those names is for the addressee, so a harness that wants to ask Carol about an invoice writes `finance` if that is her name in its team. A team that addresses none of these names is left out, and a team on another node is not here: only its own node knows its names.
- It holds labels, departments, roles and what to ask about: **never a key, a device, an account, an address, an email, or a phone number**, because the definition holds none of them for a seat or an external party and this is not the place to add them for a member.
- The sample, with made-up names, is `testdata/directory.sample.json`.

## Devices (kind `device`)

A device change adds or removes one of a member's devices:

```json
{ "org": "acme", "account": "bob", "op": "add",
  "device": { "id": "phone", "label": "Phone", "publicKey": "...", "addedAt": "2026-11-24T12:00:00Z" },
  "at": "2026-11-24T12:00:00Z" }
{ "org": "acme", "account": "bob", "op": "remove", "device": "phone", "at": "2026-11-24T12:00:00Z" }
```

- Who signs: while the member has no devices, only the account key, and only to add the first device. After that, only one of the member's devices (named by `signer`), never the account key.
- The account's home node checks the change against its copy of the definition and relays it to the org's root node with `POST /fed/v1/orgs/<org>/devices`. It knows where the root's node is from the invite it joined with, which only the root's node creates. If that node can't be reached, the change waits in the outbox. The root's node answers with the version it wrote, and the home node keeps it. The root node checks the signature, that `account` is a member, and that `at` is at most 7 days old and at most 5 minutes ahead, then applies the change and checks the result like any version. It writes the result as the next org definition version. Like every version, that one is signed by the root key and reaches the other nodes as usual.
- Removing a device also adds its key to `revoked`, so a lost device can never sign again, under any id. A removal takes effect on each node as soon as it holds the new version, including for envelopes still waiting in outboxes: a decision the removed device signed that has not been delivered yet (the log's `queued`, or kept by a client that has not sent it) is refused when the node tries it again. A client therefore says so before it removes a device: it counts the saved and not delivered decisions the device signed (the log's `signer`), and says how many it cannot attribute (entries with no `signer`). It does not offer to remove this device while it holds decisions of its own that the node has not taken.
- Adding a device works like this:
  1. The new device asks its home node to add it, through the Client API. The node keeps the request for an hour, and at most 10 requests for each account or hosted member: a guest's requests are its member's alone (see "Client API", "Guests").
  2. The person compares pairing codes. For the first device, the node's terminal shows the code (`agency device-add`) and signs the change with the account key. No Client API route signs with the account key. For later devices, one of the member's devices lists the request and signs the change. That device can be a client, or the CLI device on the node's terminal once it has been added.
  3. A device's id is `d-` followed by its pairing code without dashes.
- Pairing: a new device shows its pairing code, the first 12 hex characters of its key's fingerprint in groups of 4 (`dbc2-9825-1c51`). The person checks that the device that signs the add shows the same code for the key it is adding. The code has 48 bits, so a node that relays the key cannot find another key with the same code while the person is pairing.

## Signed reads (kind `read`)

A node that reads a team on another node adds these headers:

- `x-agency-account`: the account id
- `x-agency-date`: the time, with milliseconds (`2026-11-24T12:00:00.123Z`), so two reads made in one second are signed differently
- `x-agency-audience` (optional): the id of the node the read is made for (the node id of its origin: 32 lowercase hex characters, see "Push payloads"). It is present only when the signature covers it.
- `x-agency-signature`: the signature of `agency/v1/read\n` + `<method>\n<path>\n<time>\n<account>`, or, when `x-agency-audience` is present, of `agency/v2/read\n` + `<method>\n<path>\n<time>\n<account>\n<audience>`. The header says which text was signed, so a node makes one check, and neither text can pass for the other (the kind lines differ).

`<path>` is the request path without its query, except on a route that takes a query (`usage`, `activity`): there it is the path with the query exactly as the route table writes it, built from the parsed values, so a signature covers the range it reads. A query that cannot be parsed (a `since` that is no RFC 3339 UTC time, a `limit` that is no number, either one missing) is checked as it was received, so that the caller is told nothing before the signature is: the answer is the same 404 as for any unauthenticated read, and a member who signed such a query gets 400.

The receiving node answers only when the time is within 5 minutes either way, the signature matches the account's public key in the org definition, and the account is a member of the team's org.
It accepts each signature once: within the 5 minutes a signature is good for, a copy of it is refused.
A read that fails any of these checks is refused like a read of an org or team the node does not have (see "Federation routes").

### A read that names the node it is for

Without it, a read made for one node verifies on any node of the org that serves the same path within the five minutes it is good for (each node accepts a signature once, but only the ones it saw). A node that is asked to take a read that names another node refuses it.

- **Who is named, and by whom.** The reader names a peer only when the `about` it kept of that peer lists the capability `readAudience` (see `docs/compatibility.md`); otherwise it makes the read as before. A node lists `readAudience` in the `about` it gives to the nodes of its org only when its `url` is a node origin (see "Push payloads"), since the id is the id of that origin, written one way; a node whose `url` is not one has no id, takes no read that names a node, and does not list the capability to them.
- **What a node checks.** When `x-agency-audience` is present, the signature is checked over the `agency/v2/read` text with that value, and the value must be this node's own id, as its configured `url` gives it: one id, never several. A value that is not a node id, or another node's, is refused like any failed read (404), with the reason in the node's log, which is always written for a read signed by a member.
- **The read of `about` is never named and is always taken either way.** It is how a reader learns the capability, so it cannot need it. Its path is part of what is signed, so a copy of it can only ever be replayed as a read of `about`, which says release, contracts and capabilities and nothing else.
- **An account that has named this node is taken no other way.** Once a node has taken a read that names it from an account (the read of `about` excepted), it takes no read that names no node from that account. The account's key is held by one node, and that node has shown it makes the new kind, so an older read of the account's that someone captured is worth nothing here. The accounts are kept in the data directory (`bound-readers.json`: account ids only), so a restart does not forget them. A file that is not there is no accounts. One that is there and cannot be read is left as it is, never written over: the node takes the accounts as none, so that reads are still answered, and says so once in its log and in `agency status`, until the file is mended or removed. An account is kept only while it is a member of an org this node has: a definition that no longer lists it drops it, and a member that comes back starts without it.
- **`federation.requireReadAudience`** in `config.json` (default `false`) makes a node take no read that names no node, from any account, except the read of `about`. It needs `url` to be a node origin (the node refuses to start otherwise). Turn it on once every node of the org lists `readAudience`.
- **`federation.unboundReadAccounts`** in `config.json` (a list of account ids, at most 100) lists accounts whose older reads the node still takes, whatever the two rules above say. It is for an account that reads from two nodes of different releases, and for an account whose node went back to a release that does not list `readAudience`: after the first read that named this node, the other node's reads are refused (404) until it is updated, or until the account is listed. The line the node writes for such a refusal says so and names the key. A reset command would be undone by the account's next read that names the node, so the key is how it is cleared: it holds as long as it is in the file.
- **What stays open.** A read made in the older form that was captured before its account first named this node, or for a node that account has never named, can still be replayed on a node that takes it, until that node requires the name. A reader makes the older form toward a peer that does not list `readAudience`. Replacing the older form for good is the overlap of `docs/compatibility.md`.

## Decision envelope (kind `envelope`)

```json
{ "id": "<32 characters>", "kind": "answer", "org": "acme", "team": "app", "target": "r-20260101-000000-abcd",
  "payload": { "text": "", "choice": "a" }, "account": "alice", "at": "2026-11-24T12:00:00Z" }
```

- `kind`: `answer` (answers a request; `target` is the request id) or `judge` (decides a board item waiting for a decision; `target` is the item's reference). Either way `target` is 1 to 120 bytes of ASCII letters, digits, `.`, `_`, `#`, and `-`; anything else is refused as a malformed target (see "Item references").
- `signer` is the id of one of the deciding member's devices. The signature is checked with that device's key, found under the member whose `account` is the envelope's `account`. A signature by an account key is refused.
- The receiving node (the team's node) applies an envelope only after checking the signature, membership, expiry (7 days after it was made, and at most 5 minutes ahead), that the envelope's org and team match where it was sent, that its id has not been applied before, that it was made after the team came to this node, and that its account is the addressee of the request it decides. The team came to its node at the time (`at`) of the oldest version in the latest unbroken run of versions that name that node as the team's `node`. An envelope made earlier was made for the node the team ran on before, which received it, and gets 400. A version that does not move the team changes nothing, nor does one that only writes the same origin another way (compared as the node writes an origin: the host lowercased, the scheme's default port left out). A real move, a rename of the node's origin included, means that a decision made before it and not yet delivered must be made again (`agency team-move` says so). When the run reaches back past an envelope's 7 days, or a version of it is not kept, nothing is refused for it. A repeated envelope is not applied again; the node answers that it received it, even if the request no longer waits. The expiry is checked before the id, so the node keeps the ids it applied only for as long as an envelope can still be accepted: 7 days and 5 minutes (the 5 minutes an envelope's time may be ahead), and drops older ones when it writes a new id; a copy within that time is still a duplicate, and one after it is refused as expired.
- The request an envelope decides is the one in the team's current view whose `answerWith` is the envelope's `kind` and `target`. Its addressee is the member the rule in "Requests" gives (the same rule as `mine`). An envelope from anyone else, or for a request that is not waiting, is refused with 403, and both get the same refusal.
- The sending node keeps an envelope it could not deliver in its outbox and retries with backoff (15 s, 30 s, 1 min, 2 min, 5 min, then every 5 min). It does not retry when the receiver refuses with a 4xx (408 and 429 are retried). The outbox sends to up to 8 nodes at once, and to each node in the order it queued (an org's versions queued in the same second in version order), so a node that does not answer holds only its own parcels (and a team's runtime on this node that does not answer only that team's decisions); once it is unreachable in a pass, its other parcels wait for their next attempt, and a version waiting for its next attempt holds back the later versions of its org for that node.
- A decision that a client sends to its home node (`POST /api/orgs/<org>/teams/<team>/envelopes`) is kept the same way, also for a team on that node: the node checks what needs no runtime and no peer, puts the envelope in its outbox and the decision log, and answers at once (202 `queued`); a background task then applies it to the team's runtime, or sends it to the team's node. The answer never waits for a runtime or a peer. For a team on this node the task retries sooner (2 s, 5 s, 15 s, 30 s, 1 min, 2 min) and gives up after 7 tries in all, when the decision becomes `refused` with the last reason; a runtime that answers 400 or 404, an envelope whose account is not the request's addressee, or an org or team that is gone, is refused at once. The envelope's id is the outbox key, so sending the same envelope again never delivers or applies it twice.
- Nodes accept envelopes signed by a device of the deciding member. The CLI signs with its CLI device, and clients send device-signed envelopes through `POST /api/orgs/<org>/teams/<team>/envelopes`. The home node checks them as the team's node will, except that the request's addressee is checked when the decision is applied (the log then says `refused`), and never signs them itself.

## Invites and joining (kind `join`)

1. The root key's node creates an invite. Invite link: `agency:join?node=<node origin>&org=<org>&fp=<root key fingerprint>&code=<code>`. The code is 16 random bytes as base64url. The node keeps only the code's SHA-256. An invite expires after 7 days and can be used once.
2. The invited account's home node reads the org definition with `GET <node>/fed/v1/orgs/<org>/definition?code=<code>` and checks that the root key's fingerprint matches the link's `fp`. If it does not, it stops (the node may be fake).
   An org id names one org on a node. If the node already has an org with the link's id (a stored definition, or a trusted root fingerprint) under another root key, it refuses the link and changes nothing: joining would replace its definition and its trust for that id, and with them the teams it hosts there. A node also never creates an org with an id it already trusts.
3. When the invited person accepts, their node signs a join request and sends it to `POST <node>/fed/v1/orgs/<org>/join`. Body: `{ "org", "code", "account", "label", "publicKey", "at" }`. The signature is checked with the body's `publicKey`, and `at` must be within 10 minutes of the root node's clock. An `account` that is one of the reserved runtime names (see "agency-runtime/1") gets 400 at once, and the invite stays unused.
4. The root key's node checks the code, its expiry, and that it is unused, signs the next version with the new member added at the place the invite set (department, role; for an invite made for a seat with `agency invite --org <org> --seat <seat>`, the seat is taken instead: see "Taking a seat" under "Org definition", and the join is refused with 409, leaving the invite unused, when the seat is not in the org any more), and returns it to the requesting node. The new version goes to the nodes of the org's teams through the outbox. When the root key asks for the owner's presence, it holds the join instead and answers `202` (see "Pending root changes"); the joiner then fetches the signed version with the handle.

## Pending root changes

A root key that asks for the owner's presence (the macOS keychain) never signs because someone else asked: a prompt that anyone can make appear teaches the owner to press without reading. So the root's node holds such changes for the owner and signs them in one run that the owner starts.

- **What is held:** a join (`POST …/join`), and a device change, whether it comes from another node (`POST …/devices`) or from a client of the owner's own (`POST /api/devices/changes`). Each is checked exactly as when it is signed at once (signature, invite, membership, time). With a root key that asks for nothing (a file, or the account key of an org made before root keys were kept apart), nothing changes.
- **The answer:** `202 Accepted` with `{ "pending": <handle>, "message": <what to tell the person> }`. The handle is 32 random bytes as base64url and is the only way to the held change. A held join's invite is used from then on; refusing the join, or its expiry, frees it again. A join the root's node neither signs nor holds (the root key refuses to sign, or too many changes wait already) leaves its invite unused.
- **The asking side:** a device change answers its client `DeviceChangeResult` with outcome `pending` and the message, and the member's node takes the version by catch-up once it is signed. A joiner keeps the handle and asks `GET /fed/v1/orgs/<org>/joins/<handle>` (in the background, and with `agency sync`): `202` with the same body while it waits, `200` with the signed version once signed (the joiner reads the versions between the definition it checked the invite with and this one from the root's node, now that it is a member, and checks each as the root-signed successor of the one before; the last must name it), and 404 once the change was refused, expired, or never existed.
- **Signing:** `agency root-sign` lists every held change (its handle, what it changes, when it came) by org, asks to sign each org's list, and then signs **only those changes**, in the order they came, each as its own version, after one presence prompt **per three changes** whose words name every one of them (`Sign 3 changes for acme: add member carol (Carol), add device iPhone for bob, remove device d-… of bob`). A member taking an id into its `formerly` (a seat claim, which moves to it what was addressed there) or giving one up is always named, however many other changes the version makes (`bob takes seat finance (Finance)`; an id that is no seat says so: `bob takes alice, which is no seat`). It asks on the terminal before each prompt, and a run of more than three is refused. A label from someone else is shown with every control character and every character that could reorder a line or hide in it (the list in `is_hidden_char` and `testdata/label-hidden-chars.json`: Unicode Cc, U+2028, U+2029, the bidirectional controls, U+200B, U+2060 to U+206F, U+00AD, U+180E, U+FFF9 to U+FFFB, U+FEFF, U+E0001) as `?`, here and wherever the node prints one, and a label this node writes now may not hold one; the joiners U+200C and U+200D and the emoji tags stay. A change that no longer holds against the org as it is then (the joiner is in, the device's key was revoked, an account key that may add only a first device) is dropped and said so. A refused prompt signs nothing and leaves every change waiting. `agency root-sign --refuse <handle>` drops one.
- **Limits:** at most 5 changes are held for one account in one org (409 beyond). A joiner's label must be 1 to 80 characters with no control character. A held change is dropped 7 days after it came (`PENDING_ROOT_DAYS`), by the node's own loop as well, which frees a held join's invite.
- **The owner sees them:** `/api/me` gives the owner `rootChanges`, oldest first and absent when none: `{ id, org, kind, member, label?, device?, what, receivedAt }`, where `kind` is `addMember` (`label` the new member's name), `addDevice` (`label` and `device`, the device's id), or `removeDevice` (`device`), and `member` is the joiner or the device's owner. A client words it from `kind` in the screen's language and shows the English `what` only for a kind it does not know, and `agency status` counts them per org.

## Federation routes

| Method | Path | Checked |
|---|---|---|
| GET | `/fed/v1/orgs/<org>/definition` | A member's signed read, or an open invite code |
| POST | `/fed/v1/orgs/<org>/definition` | It is the next version (signed by the root key) |
| GET | `/fed/v1/orgs/<org>/about` | A member's signed read of the org. Answers `About` (see "Discovery"): the release, the contracts and the capabilities of this node, and never `oldestApp`. A stranger, a signature for another path, a copy of a read already answered, and an org this node does not have are all refused alike (404) |
| GET | `/fed/v1/orgs/<org>/versions?after=<n>` | A member's signed read of the path with its query. Answers `{ "versions": [<signed definition>, ...] }`: the versions after `n`, oldest first, at most 20 (a node further behind asks again); 404 when this node does not have them all |
| POST | `/fed/v1/orgs/<org>/join` | The join request's signature and the invite. Answers the version it signed, or `202` with a handle when the root key asks for presence (see "Pending root changes") |
| GET | `/fed/v1/orgs/<org>/joins/<handle>` | Only the handle: `202` while the held join waits, `200` with the signed version, 404 otherwise |
| POST | `/fed/v1/orgs/<org>/devices` | Only on the root's node (403 elsewhere, once the change's signature checks out): a device change, checked as in "Devices". Answers the version it wrote, or `202` with a handle when the root key asks for presence |
| GET | `/fed/v1/teams/<org>/<team>/view` | A signed read and membership (answers `{ "view": TeamView, "viewer"?: <name>, "answersFor"?: [{ "name": <name>, "id": <id> }] }`) |
| GET | `/fed/v1/teams/<org>/<team>/usage?days=<n>` | A signed read of the path with its query, and membership (answers `TokenUsage`; 400 for a range outside 1 to 90; 404 when the team's runtime does not report usage) |
| GET | `/fed/v1/teams/<org>/<team>/activity?since=<time>&limit=<n>` | Like `usage`: a signed read of the path with its query, and membership as a member (an answerer gets 403). Answers `Activity` (see "Activity") for the events after `since` (an RFC 3339 UTC time), at most `limit` (1 to 500; both are needed, the reader's node sends its defaults); 400 for a value outside that after the read is authenticated; 404 when the team's runtime does not report activity. The reader's node checks the answer as it does a runtime's (`Activity` check) and answers 503 when it is malformed |
| GET | `/fed/v1/teams/<org>/<team>/evaluation?days=<n>` and `/effort?days=<n>` | Like `usage`: a signed read of the path with its query, and membership as a member (an answerer gets 403). Answers `Evaluation` or `Effort` with that one team in `teams` or `unavailable`; 400 for a range outside 1 to 90 |
| POST | `/fed/v1/teams/<org>/<team>/envelopes` | The envelope's signature, membership, expiry, and that it was not applied before |

The federation routes bypass Cloudflare Access, so anyone can call them, and nothing in an answer may tell a caller what the node holds until the caller is authenticated.
Every request that fails before that gets `404` with the body `{"error":"not found"}`, whatever the reason:

- the org or the team is not on this node, or its id is malformed;
- a signed read is missing, malformed, more than 5 minutes off the node's clock, signed by a non-member, or signed by another key;
- an envelope names a non-member, a device the member does not have, or is not signed by that device's key;
- a device change names another org or a non-member, or is not signed by the key that "Devices" requires;
- an org definition is not signed by the root key the node knows for the org (the root of its copy, or, without a copy, the root whose fingerprint it trusts).

A node never follows a redirect in an answer to its own requests (to other nodes, to the Access certs, or to APNs): others choose where it sends, and a redirect would carry its signed requests elsewhere. A 3xx answer is a failed one.

The node writes the real reason for such a refusal to its own log, never to the caller: at most 20 lines a minute, then a count of the rest, except that a refusal of a request with a valid signature by a member (for example one whose clock is off) is always written.

Once the request is authenticated, refusals are specific (an expired envelope, a version that is not the next one, a node that does not hold the root key).
A request whose signature is well formed spends one signature check even when the org, team, member, or device is missing, so the time of an answer does not tell either (apart from reading the node's files).
The checks that do not depend on what the node holds come first and answer as they always do: a malformed body (400), an envelope whose org and team differ from the path (400), and a join request (whose invite code is its credential: 403 for an unknown, used, or expired code, also in an org the node does not have).

## TeamView

A TeamView is what a team runtime reports about its team: its participants (`people`), the requests waiting for a decision, its work items, and its epic forecasts.
The node reads it from the team runtime (`view` in agency-runtime/1), returns it from `GET /fed/v1/teams/<org>/<team>/view` as `{ "view": TeamView, "viewer"?: <runtime name>, "answersFor"?: [{ "name": <runtime name>, "id": <org id> }] }`, and serves it to clients.
`viewer` is the signed reader's name in the team runtime (see "Requests" below for the mapping); it is absent when the team does not address the reader.
`answersFor` lists the seats and external parties the reader answers for in that team: for each entry of the team's `people` that names a seat or an external party the reader answers for (see "Requests"), the runtime name a request's `to` holds, and the party's id. An id in the reader's own `formerly` counts as a party, as a seat or an external party does. It is ordered by name, and absent when there is none, as it is from a node that does not send it. The reader's home node keeps it with the replica, and takes the label of each party from its own copy of the org definition, never from the team's node. It reads at most 200 entries, with names of at most 200 characters, and drops an answer beyond that as it does a view beyond the limits.
A node that reads another node's TeamView parses it into these types before keeping a replica, and drops it if it does not parse or is beyond the limits below. It reads at most 2 MiB of any answer from another node. Every 30 seconds it re-reads the replica of every team on another node, up to 8 at a time, and at the same time each other node's `about` and the org's definition (from a node whose team last answered); the push pass and the outbox run on their own schedules, so a node that does not answer delays none of them.

Limits, in characters for text: ids, labels, names, and refs 200; a request's or work item's `title` 200; `context` 4,000; `document` 40,000; a person's `status`, an option's `text`, and a forecast's `basis` 500; an option's `detail` and a thread message 4,000. At most 200 people, 200 requests, 5,000 work items, 500 epics, 20 options per request, 200 thread messages, and 100 entries in `holding`, `blocks`, or an epic's `blocked`. A node serves a runtime's view only within them too (`agency_proto::view::limits`).

The Rust types in `agency-proto` (`view.rs`, `runtime.rs`, `timestamp.rs`) are the source of truth.
The TypeScript types in `bindings/` are generated from them with ts-rs and are never edited by hand; `scripts/check-bindings.sh` regenerates them and fails on any difference.
`testdata/teamview.sample.json` is the shared sample: the Rust tests, the web client, and the harness all read it.

Conventions:

- Keys are camelCase. Numbers are non-negative integers.
- `Timestamp`: RFC 3339 in UTC, ending in `Z` (`2026-11-24T12:00:00Z`; fractional seconds are allowed). `Date`: a calendar date, `YYYY-MM-DD`. They are different types.
- An optional field is omitted when absent. It is never written as `null`.
- Participants and addressees are named by the team runtime's own names (for example a session name, or `owner`), not by Agency org member ids. The team runtime does not know org member ids, except the one the node gives it in a decision (`by`), which is why a thread message can carry it (below).
- Unknown fields are ignored, so a team runtime may add fields before the contract names them.

```
TeamView      { org: Id, team: Id, label, generatedAt: Timestamp,
                people: PersonStatus[], requests: Request[], work: WorkItem[], epics: EpicForecast[] }
PersonStatus  { id, label, kind: "agent" | "human", role: "lead" | "member",
                state: "working" | "idle" | "away" | "unknown", since?: Timestamp,
                waitingOn?: { kind: "person", person } | { kind: "lead" },
                status /* one line */, holding: string[] /* work item refs */ }
Request       { id, kind: "question" | "proposal" | "pendingDecision", title, context /* plain text */,
                document?: string /* Markdown, proposals */, from, to?, createdAt: Timestamp,
                issue?: string, blocks: string[], options: RequestOption[], thread?: ThreadMessage[],
                answerWith: { kind: "answer" | "judge", target } }
RequestOption { key, text, isRecommended: boolean, detail?: string }
ThreadMessage { from, text, choice?: string, by?: Id, at: Timestamp }
WorkItem      { ref /* item reference */, title, status: "backlog" | "next" | "inProgress" | "release" | "done",
                assignee?: string, blocked?: { reason: BlockedReason, since: Date }, epic?: string,
                points?: number, eta?: { p50: Timestamp, p80: Timestamp, basis, isOverBudget: boolean },
                workType?: WorkType, doneAt?: Timestamp }
WorkType      "newFeature" | "improvement" | "maintenance" | "debt" | "incident"
BlockedReason "needsDecision" | "external" | "waitingOnPrevious" | "timeOrEquipment"
EpicForecast  { ref, title, total, done, doing, remainingPoints, blocked: { reason: BlockedReason, count }[],
                forecast?: { days, at: Timestamp }, doneAt?: Timestamp, basis }
```

Item references:

- A work item is named by an **item reference** (`WorkItem.ref`, `EpicForecast.ref`, and where a work item is named: `WorkItem.epic`, `Request.issue`, `Request.blocks`, `PersonStatus.holding`). It is an opaque string that the team's harness chooses, for example `app#12` or `ENG-123`. Nothing in a node or a client splits it, reads a number out of it, or builds a link from it, and two references are the same only when the strings are equal. A view allows 200 characters.
- One use is stricter. The `target` of a `judge` envelope is an item reference, and an envelope's `target` is checked by the node (400, `malformed target`) and by the iPhone app before it signs: 1 to 120 bytes of ASCII letters, digits, `.`, `_`, `#`, and `-`. So a pending decision's `answerWith.target` has to follow that rule, even where `ref` and `issue` are longer or hold other characters (`owner/repo#12`, a URL).
- A runtime whose tracker's ids do not fit gives the pending decision a reference that does (for example `PROJ-12`, or a short hash), keeps a lookup from it to the item, and reads it back in `decide`. The item's `ref` and `issue` may stay as the tracker writes them. The rule is widened only when a real tracker needs it, because every node and the app must accept the wider rule before a harness sends it.

Participants (`people`, humans and agents):

- `state` says whether the participant is active; `waitingOn` says who has to act before they can continue. A participant can be `working` and still wait on someone, for example on a permission prompt: then `waitingOn` names the participant who answers the prompt and `status` says it is a permission prompt.
- `waitingOn.person` uses the same names as `Request.to`.
- Who waits on the reader is decided by the reader's home node and given to clients as `TeamSnapshot.waitingOnViewer`: the `id`s of the participants whose `waitingOn` is `person` with the reader's runtime name in that team (`viewer`). Unlike a request's `to`, a name that is not the reader's is never theirs, because `waitingOn` can name anyone on the team, agents included. A reader the team does not address (no `viewer`) has nobody waiting on them.

Work items:

- `workType` is the board's "Work type" field of the item (see "Work type" in the glossary), as the team's runtime reads it. It is left out when the board has none; a runtime never guesses it, and whoever needs a type for an item without one (the node, when it splits effort by work type) works it out from the item's pull request itself. A value outside the five names fails the view's parse, like any other malformed field.
- `doneAt` is when the item first reached `done`: the board's own time when the tracker has one, otherwise when the runtime first saw it (up to one refresh late). It is left out while the item is not done and when it is not known; an item that goes back and is done again keeps the first time. `EpicForecast.doneAt` is when the epic's last child reached `done`, present only once `done` equals `total`. A runtime may keep a finished epic in `epics` for a while so that this time can be read (the scrum harness keeps it 30 days): it has `done` equal to `total`, nothing `doing`, nothing remaining, and no `forecast`, and a client shows it as finished, after the open epics, and does not count it in what remains. `work` lists open items only, so `WorkItem.doneAt` appears only on an item still in the view. The node passes both on unchanged.

Requests:

- `question`: the team asks something. `proposal`: the team asks for approval of a document (`document`) with options. `pendingDecision`: a board item is blocked until someone decides.
- `answerWith` is exactly the `kind` and `target` of the decision envelope that answers the request, so clients never derive them. A `pendingDecision` is answered with `judge` and its item reference; the others with `answer` and the request id. So the `answerWith.target` of a pending decision follows the stricter rule of "Item references" below.
- `to` absent means the team's owner. The node maps runtime names to org members through its hosted-team configuration: `owner` is the org member id of the team's owner, and the optional `people` map names other runtime names (`{ "<runtime name>": "<org member id>" }`). A `to` that is not in `people` goes to the owner.
- In the other direction, an org member's runtime name is their key in `people`; otherwise `owner` if they are the team's owner; otherwise they have none in that team.
- Which requests are a reader's to decide ("mine") is one rule, computed by the reader's home node and given to clients as `TeamSnapshot.mine`. The desk, the badge counts, and push notifications all use it, and the team's node applies a decision only from the member it gives (see "Decision envelope").
  - In a team on that node, a request is the reader's when its addressee, as above, is the reader, or is a seat or an external party that the reader answers for. So a request with no `to`, or with a `to` that is not in `people`, is the team owner's.
  - A `people` entry may name a seat or an external party of the org (`"finance": "carol"`), or a seat that a member took, and a request addressed to a seat that a member took is that member's own, answered by them and no one else (there is nothing to answer for). A request addressed to a seat or an external party is answered for them: by each member in their `relays` (in any order), and by no one else, the owner included; a seat with no `relays` is answered for by the team's owner. A seat and an external party answer nothing themselves, and a request addressed to an id that is none of member, seat, or external party is answered by no one (the node warns at start about such an entry). It is one rule, `is_addressed_to`: the list of a reader's requests (`mine`), what an answerer reads, and the team node's check of an envelope all call it, so a member is never shown a request they could not answer and never answers one they cannot see.
  - A request addressed to a seat or an external party is shown with whom it is for: `TeamSnapshot.relayedFor`, for a team on the reader's own node and for one on another node alike. For a team on another node, the home node says it only of a seat or external party that its own definition has and in whose `relays` the reader is (a seat with no `relays` is answered by the team's owner, whom only the team's node knows); what the team's node says is not enough. The decision log's `relayedFor` follows the same rule.
  - In a team on another node, the home node knows the reader's runtime name there (`viewer`) and the seats and external parties the team's node says they answer for (`answersFor`). A request is the reader's when its `to` is that name, or when it has no `to` and that name is `owner`, or when its `to` is the `name` of an `answersFor` entry, or the id of a seat that is in the reader's own `formerly` (a seat the reader took, which the team's node may still name in its `people` and so list in `answersFor`; that request is the reader's own, so `relayedFor` has no entry for it); the label in `relayedFor` is that entry's party as this node's definition of the org has it, under the rule above; when the definition has no such party, or does not have the reader answer for it, there is no label (the request is still the reader's). A reader who owns that team under another runtime name is not given the requests without `to`; this is a known limit.
  - A reader the team does not address (no `viewer`) has only the requests of the seats and external parties in `answersFor`, if any.
- `context`, `detail`, `status`, and messages are plain text. `document` is Markdown; clients render a safe subset and never render raw HTML from it.
- `thread` holds earlier messages, oldest first, when a request was answered and then reopened.
  - `from` is the runtime's name of the participant the message is from. `by` is optional and, when a message carries a decision, names the org member who decided: an `Id`, the `by` of the decision the node passed to the runtime (see "agency-runtime/1"), never a participant name. A message the team wrote has no `by`. A `by` that is not a valid `Id` makes the whole view fail to parse, like any other malformed field.

## agency-runtime/1

The node does not read or write a team runtime's files. For each hosted team it runs a configured command (argv and environment) once per call:

1. It writes one JSON request to the command's stdin and closes stdin.
2. It reads one JSON response from stdout. Text in a decision travels only on stdin, never in arguments.
3. The command exits with 0 when the response is a result and 1 when it is an error. The node stops the command after 20 seconds and treats that as unreachable.

Request: `{ "runtime": "agency-runtime/1", "org": <Id>, "team": <Id>, "op": <op>, ...input }`.
Response: `{ "result": <result> }` or `{ "error": { "status": <HTTP status>, "message": <text> } }`.

| op | input | result |
|---|---|---|
| `describe` | none | `{ "runtimes": ["agency-runtime/1"], "ops": ["describe", "view", "decide"], "label": <text> }` |
| `view` | none | TeamView |
| `decide` | `"decision": { "kind": "answer" \| "judge", "target", "by": <org member id>, "byParticipant"?: <participant name>, "onBehalfOf"?: <seat or external party id>, "payload": { "text", "choice"? } }` | `{}` |
| `tokenUsage` (optional) | `"days": <1 to 90>` | `TokenUsage` (see "Token usage") |
| `activity` (optional) | `"since": <Timestamp>`, `"limit": <1 to 500>` | `Activity` (see "Activity") |
| `participantMetrics` (optional) | `"days": <1 to 90>`, `"utcOffsetMinutes"?: <-720 to 840>` | `ParticipantMetrics` (see "Participant metrics") |

- The node calls `describe` first and stops unless `runtimes` contains `agency-runtime/1`. Unknown names in `ops` are ignored.
- It runs at most one `view` and one `tokenUsage` per team at a time. Callers that arrive meanwhile share the answer, and the node reuses usage for 60 seconds (for the same range).
- **A read waits for no runtime process once the node has an answer.** The node keeps each team's last view (and its activity window) in memory. A view younger than 5 seconds (activity: 10) is served as it is. An older one, up to 60 seconds old, is served at once and one refresh starts in the background. Only a read with nothing in memory, or nothing younger than 60 seconds (the first read of a team, or after the runtime has failed that long), waits for a run, and readers that must wait share the run already in flight. So a view or an activity read can be up to 60 seconds old; the runtime's own `generatedAt` says when it was made. A refresh that fails keeps the last good answer until it is that old, and then the failure is answered. The node counts the reads that were served young, served old, and had to wait, so cold reads can be told from warm ones.
- A decision goes to the runtime directly. It drops what is kept for the team and starts a refresh of its view at once, so the read that follows finds a fresh answer or joins the run in flight.
- The node calls `decide` only after it has verified the decision envelope (signature, membership, expiry, team, replay, and that the decider is the request's addressee, or answers for the seat or external party it is addressed to). `onBehalfOf` is the id of that seat or external party when `by` answered for it, and is absent when the request was `by`'s own; a runtime that does not know it ignores it. `by` is the org member who decided, and `byParticipant` the same decider as a participant of the team: their runtime name, in the same name space as a request's `to` (their key in the hosted team's `people`, otherwise `owner`). The node sends `byParticipant` with every decision; a runtime should refuse (404) a decision on a request whose `to` names another runtime name. The node maps a `to` it does not know to the owner, and the runtime does not know the map, so for such a request only a decision with `byParticipant` `owner` is the addressee's.
- **Reserved names.** `owner`, `board`, and `unverified` are names a runtime gives meaning of its own: `owner` is the team's owner, as above, and the other two are participants of the reference runtime that are no org member. Since a runtime reads `by` as well as `byParticipant`, the root's node never signs a version that newly gives one of them as the id of a member, a seat, or an external party (400), and `agency init` refuses one as the account. One that a version already has is kept, so that the org still signs its other changes. A runtime should decide who decided from `byParticipant`, never from `by`.
- Error statuses: 400 (malformed input), 404 (no such request or work item), 503 (the runtime cannot act now). The node treats 400 and 404 as refusals and does not retry them; it retries every other failure, including a timeout or output that is not a response.
- `tokenUsage` is optional. The node calls it only when `describe` lists it in `ops`; otherwise it answers 404 without running the command. A runtime's 404 also means it has no usage to report; any other failure is 503.
- `activity` is optional in the same way: the node calls it only when `describe` lists it, and otherwise answers 404 without running the command. It runs at most one `activity` call per team at a time, and the answer is kept and refreshed as above (young for 10 seconds): the command is asked for the events after five minutes before the first reader's `since`, at the largest `limit`, and each reader gets the events after its own `since`, cut at its own `limit`, so readers with different questions start one process. A reader whose question the shared answer cannot give (it asks from before the shared answer began, or for more events than an answer the runtime cut holds) gets a run of its own.
- `participantMetrics` is optional in the same way: the node calls it only when `describe` lists it, and a runtime without it is a team with no participant metrics, not an error. A runtime that lists it cuts the days at `utcOffsetMinutes` when the request has it.
- `usage` is a reserved op name. Subscription usage belongs to the account, not to a team runtime, and is not part of agency-runtime/1.

## Token usage

```
TokenUsage  { org: Id, team: Id, days, generatedAt: Timestamp, byDay: DayCost[], byPerson: PersonUsage[] }
DayCost     { date: Date, costUsd: { <runtime name>: number } }
PersonUsage { person: <runtime name>, costUsd: number, tokens: { input, output, cacheRead, cacheWrite } }
```

- A report covers the last `days` calendar days, today included, in the team runtime's time zone. `byDay` is oldest first; days without use may be left out.
- Participants are named by their runtime names, as in TeamView, not by org member ids.
- `costUsd` is an estimate: tokens priced at API rates, in US dollars rounded to cents by the runtime, whatever actually pays for them (a subscription or an API key). It is the one exception to "numbers are non-negative integers": a non-negative JSON number. Token counts are non-negative integers.
- The node computes nothing and stores nothing; every read asks the team's runtime. Before passing a report on, the node checks that `org`, `team`, and `days` are the ones it asked for, that `byDay` has at most `days` entries with strictly increasing dates, that every cost is finite and non-negative, and that every participant has a name. A report that fails is 503.
- The shared sample is `testdata/tokenusage.sample.json`.

## Participant metrics

What a team runtime knows about each participant's days, and whose pull requests were whose. It is the optional op `participantMetrics` of agency-runtime/1, and it carries only what GitHub does not have: the times of the pull requests and of the issues (when one opened, merged, or moved to In Progress) are GitHub's, which the node reads for "Evaluation", so no second source of the same times exists. A work item's work type and epic are in the `TeamView`, and so are not here either.

```
ParticipantMetrics { org: Id, team: Id, days, generatedAt: Timestamp, utcOffsetMinutes, participants: ParticipantDays[], pullRequests: PullRequestAuthor[] }
ParticipantDays    { name: <runtime name>, byDay: ParticipantDay[] }
ParticipantDay     { date: Date, busySeconds, waitingSeconds, idleSeconds, costUsd: number, tokens: { input, output, cacheRead, cacheWrite } }
PullRequestAuthor  { repo: "owner/name", number, by: <runtime name> }
```

- A report covers the last `days` calendar days (1 to 90), today included. The days are cut at `utcOffsetMinutes`, minutes east of UTC (-720 to 840): the offset the node gave in the request, which is its own time zone, so that a day here is a day of "Evaluation"; or, when the request has none, the runtime's own. The report says which one it used, and the node refuses a report that used another than the one it asked for.
- `participants` are named by their runtime names, as in `TeamView` and `TokenUsage`, not by org member ids, and each appears once. `byDay` is oldest first; days with nothing in them may be left out.
- The three times of a day add up to the time at least one of the participant's sessions was alive. When several sessions overlap, the overlap counts once, not once for each. `busySeconds` is the time at least one session was working. `waitingSeconds` is the rest of the time in which at least one session waited for a decision of a human. Only a human's decision is waiting: a session that waits for an agent participant, or for anything else, is idle in that time, so that two runtimes cannot split the same minute differently. `idleSeconds` is the rest: sessions were alive and none worked or waited. A moment that is both busy and waiting is busy. Time in which no session was alive is in none of them, so a day's three numbers may add up to less than the day. A day is cut at a fixed offset, so it lasts exactly 24 hours (86 400 seconds) whatever the clocks do, and the three numbers never add up to more than that.
- `costUsd` and `tokens` add up over the participant's sessions, as in "Token usage" (an estimate at API rates, rounded to cents).
- `pullRequests` lists a pull request only when the runtime knows whose session made it, for example from the session's own record that it opened that pull request. It never guesses, and a pull request it cannot attribute is left out. A pull request has one author: one named for two (even two different participants) makes the report malformed, which the node refuses whole, and anything that counts them anyway counts such a pull request once, as unattributed, never twice, so that the sum still matches. A pull request is named by `repo` and `number` on GitHub, so the node joins it to the pull requests it reads from GitHub without parsing an item reference (which stays opaque, see "Item references"). `by` is the participant's runtime name.
- Before using a report, the node checks that `org`, `team`, and `days` are the ones it asked for; that `utcOffsetMinutes` is a time zone and the one asked for; that the days of each participant are in order, within the range, and no more than 24 hours of time in a day; that costs are finite and not negative; that a participant, and a pull request, is listed once, with a name and, for a pull request, an `owner/name` and a number above 0; and that the report lists at most 1000 participants and 10 000 pull requests. A report that fails is answered as an unavailable runtime, and nothing of it is used.
- The shared sample is `testdata/participantmetrics.sample.json`. Its costs and tokens are those of `testdata/tokenusage.sample.json`, split by day.

## Evaluation

How fast a team's work ships, and where its tokens go. The team's node works the numbers out (nothing is stored: each read asks GitHub and the team's runtime, and the node reuses an answer for 10 minutes), so a screen and an agent that cites them agree.

```
Evaluation       { org, days, from: Date, until: Date, generatedAt, teams: TeamEvaluation[], unavailable: TeamUnavailable[] }
TeamUnavailable  { team: Id, reason: string }
TeamEvaluation   { team, from: Date, until: Date, summary: EvaluationSummary, byDay: DayEvaluation[],
                   participants?: ParticipantEvaluation[], unattributedMerged? }
EvaluationSummary{ merged: MergedCounts, prLeadMedianSeconds?, prLeadP90Seconds?, issueLeadMedianSeconds?, issueLeadP90Seconds?,
                   mainRedSeconds, longestRedSeconds, reverts, costPerMergedPrUsd? }     // ? = left out when there is no value
MergedCounts     { feat, fix, refactor, docs, test, chore, other }
DayEvaluation    { date, merged: MergedCounts, reverts, mainRedSeconds, costUsd, prLeadSeconds: int[], issueLeadSeconds: int[] }
ParticipantEvaluation { name, busySeconds, waitingSeconds, idleSeconds, costUsd, tokens: { input, output, cacheRead, cacheWrite },
                   merged, costPerMergedPrUsd? }

Effort           { org, days, from, until, generatedAt, teams: TeamEffort[], unavailable: TeamUnavailable[] }
TeamEffort       { team, from, until, byType: ByWorkType<TypeUsage>, byDay: DayEffort[] }
DayEffort        { date, costUsd: ByWorkType<number> }
ByWorkType<T>    { newFeature: T, improvement: T, maintenance: T, debt: T, incident: T, unclassified: T }
TypeUsage        { costUsd: number, tokens: { input, output, cacheRead, cacheWrite } }
```

- The period is the last `days` calendar days (1 to 90), today included. `from` and `until` are its first and last day, written like `byDay[].date`, in the time zone of the node that computed them: each team has its own (the time zone of the team's node), and every day of its `byDay` lies inside them, so a client draws a team against its own period. The answer's own `from` and `until` are the answering node's. `byDay` is oldest first, and days with nothing in them may be left out.
- Counts and seconds are integers. Costs are estimates at API prices, as in "Token usage". An optional field is left out, never null.
- A pull request counts on the day it merged. Its type is the Conventional Commits type of its title (`feat`, `fix`, `refactor`, `docs`, `test`, `chore`); anything else, including `ci`, `build`, `perf`, `style`, is `other`.
- A **revert** is a merged pull request whose title starts with `Revert` or `revert`, or whose body has a line that starts with `This reverts commit <sha>` (what `git revert` writes) or `Reverts <owner/name>#<number>` (what GitHub's Revert button writes); a sentence that only mentions those words does not count. It is counted in `reverts` and not in `merged`, so the pull requests merged are `merged` and `reverts` together.
- **PR lead time** is opened to merged. **Issue lead time** is the issue's first move to In Progress on the board (else the pull request's first commit) to merged; a pull request with no closing issue has none.
- **Main red**: for each push to the default branch, the commit's workflow runs decide (all workflows). A commit is red when a run failed or timed out and green when all passed or were skipped; a run cancelled by a newer push counts for nothing. Red lasts from the completion of the first red commit to the completion of the next green one, or to `generatedAt` while it is red. A span across midnight is split between the days. `longestRedSeconds` is the longest single span.
- The summary's p90 is the nearest rank (`sorted[ceil(0.9 n) - 1]`); the median of an even count is the mean of the two middle samples, rounded down. A median or p90 is left out with no samples.
- `costPerMergedPrUsd` is the period's cost divided by the pull requests merged in it (`merged` and `reverts`). Token usage is per day, so there is no per-pull-request attribution. It is left out when nothing merged.
- **Work type** (`Effort`): the board's "Work type" field when the item has one; otherwise the pull request's type: `feat` is `newFeature`, `refactor` is `debt`, `fix` is `maintenance` (`incident` when its issue carries the label `incident`, compared without case as GitHub does), and `docs`, `test`, `chore` are `maintenance`. Work with neither is `unclassified`. `improvement` comes only from the board field. The node reads the field of the issues a pull request closes: the first issue, and in it the first project, that has a value of the single-select field named `Work type` is the pull request's; the option's name is compared without case, spaces, hyphens, and underscores, and only `newFeature`, `improvement`, `maintenance`, `debt` (also `techDebt`), and `incident` name a type, so `New feature` and `Tech debt` do, and any other option, or none, is no value (never a guess). A pull request that closes no issue has none. The intended allocation and budget are the org definition's team plan; `Effort` does not copy them.
- **Effort's split** is an estimate: the runtime reports cost by day, and tokens for the whole period only. A day's cost is shared out among the work types of the pull requests merged that day, one share for each pull request (a revert, and a type that is none of the above, is `unclassified`; the types are as in "Work type"). A day nothing merged on is the work of the next merges, so it is shared like the next day of the period that has a merge, and a day after the period's last merge is `unclassified` (work not merged yet); a period with no merge is all `unclassified`. A pull request counts on the day it merged, in the node's time zone, and one that merged outside the period gives no share. Each `byType[t].costUsd` is the sum of `byDay[].costUsd[t]`, and its `tokens` are the period's tokens of the team (the sum of `byPerson[].tokens` of its usage) in the proportion of the costs, each count rounded down, with what rounding left over added to `unclassified`, so that the types add up to the team's tokens as the costs add up to its cost. A team whose runtime reports no token usage, or whose facts cannot be read, is in `unavailable` with the reason, never with zero. The capability is `effort`.
- **Participants** (`participants`, `unattributedMerged`) are there only when the team's runtime lists `participantMetrics` and answered (see "Participant metrics"); without them a team's numbers are the same as before, and a node that does not know of them leaves them out. The node asks for the same `days` at its own time zone, so the days of the two are the same days, and adds up each participant's times, cost, and tokens over the period (`costUsd` rounded to cents). A participant's `merged` is the number of pull requests merged in the period (`merged` and `reverts` of the summary together) that the runtime names that participant the author of, found by `repo` and `number`; `unattributedMerged` is the rest, so that the `merged` of the participants and `unattributedMerged` add up to the summary's. A participant the runtime names only as an author has zero times. Each participant's three times add up to at most `days` times 86 400 seconds (the whole period), and a node refuses an answer that says more. What each participant did is the team owner's to read: the node works it out (and asks the runtime) only for a read by the org member that owns the team, so a read by another member, through that member's node or directly, gets the team's numbers without `participants` and `unattributedMerged`. `costPerMergedPrUsd` of a participant is their cost divided by their `merged`, left out when it is 0. Time spent waiting for a human is a lower bound where a runtime sees only some of the waits.
- A team whose answer cannot be had (not configured, its node unreachable, GitHub unavailable) is listed in `unavailable` with a reason in plain text, without a secret or an address, and the other teams are answered. A malformed answer from another node is such a failure.
- Before passing a report on, the node checks that `org` and `days` are the ones it asked for; that each `from` and `until` (the answer's and each team's) are `days` calendar days apart, counting both (`until` − `from` + 1 = `days`); that no team is named twice (in `teams` and in `unavailable`); that each team's days are in order and inside its own period, at most `days` of them; and that every cost is a number that is not negative. For a federation answer it also checks that the one team named is the team it asked for.
- The shared samples are `testdata/evaluation.sample.json` and `testdata/effort.sample.json`.

## Budget

How this week's spend stands against what the org's plan intends: `GET /api/orgs/<org>/teams/<team>/budget`, and `agency budget status --org <org> --team <team>`, which prints the same JSON as one line. The node works it out; a screen draws what it says and works out nothing (no week and no threshold of its own).

```
BudgetStatus  { weekStart: Date, team: BudgetPart, org: OrgBudget }
BudgetPart    { capUsd?: number, spentUsd: number, state: "ok" | "warning" | "over", partial?: true }
OrgBudget     { capUsd?: number, spentUsd: number, state: "ok" | "warning" | "over", partial?: true }
```

- **The week** is the Monday-based week of the answering node's time zone: `weekStart` is its Monday (`YYYY-MM-DD`), and the spend is that of the days from it through today. A day after today in a runtime's report does not count.
- `capUsd` is the weekly budget of the team's plan (`teams[].plan.weeklyBudgetUsd`, whole US dollars); it is left out for a team with no plan. The org's is the sum over the teams that have a plan, left out when none has. `spentUsd` is the cost of the week, estimated at API prices as in "Token usage"; the org's is the sum over those same teams.
- **`state`**: `over` when `spentUsd` is at or past `capUsd`, `warning` when it is at or past 80% of it (and below it), and `ok` otherwise. A team with no cap is `ok`. A team is `over` also when its org is, whatever its own spend and cap, and also a team with no plan.
- **`partial`** is left out when false and is only ever `true`. On the team it means its usage could not be read now (its runtime or its node did not answer in 8 seconds, or reports no usage): its `spentUsd` is 0 and says nothing, and a client shows it as not known, never as 0, with no state. On the org it means the usage of a planned team could not be read, or that of the team asked about (a team with no plan too): `spentUsd` is a lower bound and `state` can only be too low.
- A team the org does not have, and an org the account is not a member of, are 404. An answerer of the org gets 403, as for usage. It is not an in-node read (it asks the teams' runtimes and nodes), and it is in the group `usage` of the metrics.
- The capability is `budget`. The shared sample is `testdata/budget.sample.json`.

## Activity

What moved in a team lately, for a page that shows the work going forward: board events, pull requests, and which participant messaged which. Board events and message edges only; a message is told by its sender, its recipient, and the short summary its sender gave, and its body never leaves the team's runtime.

```
Activity      { org: Id, team: Id, generatedAt: Timestamp, events: ActivityEvent[], truncated: boolean }
ActivityEvent { id, at: Timestamp, kind, ...the fields of its kind }
itemAdded     { ref, title, assignee?, epic? }
statusChanged { ref, title, from: WorkStatus, to: WorkStatus, epic? }
prOpened      { ref, title, by?, issue?, epic? }
prMerged      { ref, title, by?, issue?, epic?, leadSeconds?: integer }
message       { from, to, summary }
```

- The events after `since`, at most `limit`, oldest first: every `at` is strictly after `since`, `at` never decreases, and events with the same `at` keep the runtime's order (by `id`). `truncated` is true when `limit` cut the list: there are events after the last one, and a read with `since` set to its `at` returns them (an event can share that time with the last one returned, so a client drops what it has by `id`).
- `id` is 1 to 64 characters of `a-z`, `0-9`, and `-` (the runtime uses a prefix and hex digits), unique in an answer and stable across answers. `ref`, `epic`, and `issue` are item references; `by`, `from`, and `to` are names of the team's runtime (`to` need not be a participant of the team); titles and names are at most 200 characters, a `summary` at most 120 (empty when the sender gave none, never taken from the message). `epic` is the parent epic of the item. `leadSeconds` is the time from a pull request's opening to its merge, when both are known. `assignee` is given only when the runtime knows it at the time.
- The times of `itemAdded`, `prOpened`, and `prMerged` are the times they happened; a `statusChanged` is the time the runtime first saw the change, up to one refresh interval late. The runtime keeps its log for a limited time (24 hours for the scrum harness); an older `since` answers what the log has.
- A reader accepts an event of a kind it does not know as left out, so the feed keeps working when a runtime learns a new kind.
- Before passing an answer on, the node checks that `org` and `team` are the ones it asked for, that there are at most `limit` events, their order and times as above, their ids, and the text limits. An answer that fails is 503.
- An answerer reads none of it (403). The Client API route is in "Client API"; it reads a team on another node live from that node over the federation route (`/fed/v1/teams/<org>/<team>/activity`), and checks the answer as above before it passes it on.
- The shared sample is `testdata/activity.sample.json`.

## Outcomes

The numbers of what the org's work achieves. What the org measures (its KPIs) and what a team aims at are in the signed org definition, with no number (see "Org definition"). The numbers themselves are business data: they are kept **only on the owner's node** and read **only by the owner**. They are never in the org definition, a federation route, `Evaluation` or `Effort`, a push notification, a log line, or the output of `agency status` (a count at most).

```
Observation      { kpi: Id, date: Date, value: number, source: Source, enteredAt: Timestamp, enteredBy: Id, note?: string }
Source           { kind: "manual" } | { kind: "connector", name: string }
ObservationInput { kpi: Id, date: Date, value: number, note?: string, connector?: string }
Outcomes         { org: Id, days, from: Date, until: Date, generatedAt: Timestamp, series: KpiSeries[] }
KpiSeries        { kpi: Kpi, points: Observation[], before?: Observation }
```

- An observation is one number for one KPI on one day. `date` is a calendar day in the node's time zone, the same days the delivery reports use (`Evaluation`), so a screen can draw a KPI and the cost on the same days; for a monthly figure it is the last day of the period. It is not more than one day ahead of the node's today and not older than ten years. `value` is a finite number of at most 1e15 in size, in the unit of its KPI, and no range is checked for any unit (a negative number is allowed): `money` is an amount in the KPI's own currency, never converted; `percent` is a number of percent (41.5 means 41.5%, and it can be above 100); `count` is a plain count; `ratio` is a plain number (1.5 means 1.5 times); `seconds` is a duration in seconds. **Values are for reading how a measure moves, not for accounting**: they are numbers in a JSON, not amounts in a ledger.
- `enteredAt` is the node's clock and `enteredBy` the org member id of the node's account; the one who enters a number sets neither (`ObservationInput` has no such field, and any field it does not know is refused). `source` is `manual`, or a connector's name when the number was entered with `connector` (a program the owner runs; connectors use the same route). A `note` is at most 200 characters and a connector's name at most 80, neither with a control character.
- Append-only. A second entry for the same KPI and day wins in every reading, and the first stays in the history, so a correction is visible. A KPI keeps at most 5,000 observations (409 beyond it). An observation is refused (404) when the node's account is not a member of the org or the org's definition does not list its KPI.
- `Outcomes` has a series for each KPI of the definition, in its order. `points` are the numbers of the period, oldest first, one for each day (the latest entry of that day); `before` is the last number before the period, the baseline a movement is read from. `days` is 1 to 90 (default 14), and `from`, `until`, and `generatedAt` mean what they mean in `Evaluation`: the last `days` calendar days up to today in the node's time zone. Nothing here is read from another node: unlike `Evaluation`, `Outcomes` has no federation route.
- **Every route is owner-only**: a direct local request, or one through Access signed in as `ownerEmail`. Any other signed-in email gets 403, also on a read, unlike the rest of the Client API, because someone who may read a team's board must not read the revenue. A POST also needs the write token like any write. An agent on the owner's machine reads and writes as the owner does. Letting a member read is a later decision (a role), and the default stays closed.
- An `ObservationInput` is plain JSON, not canonical JSON: it is not signed, and `value` is a decimal, which canonical JSON (integers only) has no place for. A client writes it with its ordinary JSON writer.
- The node keeps the numbers in `outcomes/<org>.jsonl` of its data directory (the directory with mode `0700`, the file `0600`), one line for each observation. **Back this directory up and keep it out of anything shared**: it is business data.
- The shared sample, with made-up figures, is `testdata/outcomes.sample.json`.

### Readings

For each aim of each team's plan, the owner can read how the KPI's numbers stand around the day the epic shipped. It is arithmetic on the owner's own numbers, **a correlation and never a cause**, and it never says whether a movement is good: the KPI's `goodWhen` is on its series.

```
Readings    { org: Id, generatedAt: Timestamp, readings: AimReading[] }
AimReading  { team: Id, epic: string, epicTitle?: string, kpi: Id, shippedOn?: Date, state: ReadingState,
              points?: number, needs?: number, readableFrom?: Date,
              before?: Observation, after?: Observation, change?: number, changeRatio?: number,
              overlapping: string[], basis: "correlation" }
ReadingState "notShipped" | "shipDateUnknown" | "noBaseline" | "tooEarly" | "noFollowUp" | "tooFew" | "ready"
```

- `shippedOn` is the calendar day, in the node's time zone, of the epic's `doneAt` (the time its last child was finished, in its team's view). A reading is made for each aim, in the order of the definition.
- The constants are part of the protocol, so that a screen and an agent that cite a reading agree: a number counts as **before** when it is dated on or before the ship day and not more than **90 days** earlier, and as **after** when it is dated at least **14 days** after the ship day (the effect needs time to show) and not more than **90 days** after it; a reading needs at least **3** numbers of the KPI in the 180 days around the ship day. `before` is the last number of its window and `after` the first of its own; `change` is `after.value - before.value`, and `changeRatio` is the change over `before.value`, left out when `before.value` is 0.
- `state` says why a reading has numbers, or why it has none, and **numbers are given in `ready` and only there**: `notShipped` (the epic is not finished: nothing to compare); `shipDateUnknown` (no ship day is known: the epic is finished and the harness could not know the time, or the team's view does not list the epic, because it is older than what the harness keeps and the node had not remembered it, or its reference names nothing there, or the node has not read the view yet; nothing is guessed from an epic that is not listed); `noBaseline` (no number in the 90 days up to the ship day); `tooEarly` (no number yet at least 14 days after, and the 90 days after the ship day are not over; `readableFrom` is the first day a number dated then would count); `noFollowUp` (the 90 days after the ship day are over and no number was dated at least 14 days after it: there is nothing to compare, and there will not be); `tooFew` (fewer than 3 numbers around the ship day: `points` says how many there are and `needs` how many are needed, 3); `ready`. A reading that refuses is the honest answer, not an error: a KPI the owner enters once a month will often be `tooFew` for a long time.
- `basis` is always `correlation`: the figure moved after the work shipped, which does **not** say that the work moved it. `overlapping` lists, in a `ready` reading (it is empty in every other state), the other epics (by item reference) that aim at the same KPI and shipped between `before` and `after`, in the order they shipped: their effects cannot be told apart from this one's, so the reading names them and does not try.
- The node **remembers each epic's ship day**, because a team's view keeps a finished epic only for a limited time (30 days for the scrum harness) while the window runs 90 days past it: `outcomes/<org>.ships.jsonl` in its data directory (the same directory and modes as the numbers) holds `{ team, epic, shippedAt }`, written the first time the node sees the epic's `doneAt` and never changed, by the node's own loop and when the owner reads the readings, and only for epics that an aim names. It is delivery data, not a business number, and is read only through the owner-only routes.
- Like every route of the numbers, it is owner-only. The shared sample, with made-up figures, is `testdata/readings.sample.json`.

## Metrics

What a node measured of itself: how long it takes to answer, and how its own calls go. It is the node's own data and is read only by its owner; no other node reads it, and it is never in a federation route. Every request the node answers is timed by the route template it matched (the middleware names it from the router's matched path only, so no id, query, or header is in a name), a request that matched no route is the one series `unmatched` (the web client's files, every 404, every scanner), and a method outside the standard set is `OTHER`. The numbers are kept by hour in files of the node's data directory (`metrics/YYYY-MM-DD.jsonl`, readable by its account only, 30 days) and read through `GET /api/metrics` (see "Client API"), by the owner only.

```
Metrics    { from: Timestamp, until: Timestamp, generatedAt: Timestamp, budget: { inNodeReadP95Ms }, objectives?: ObjectiveResult[], series: Series[] }
ObjectiveResult { group, p95Ms, state: "met" | "notMet" | "undetermined" | "unknown", measuredP95Ms? }
Series     { kind: "serve" | "call" | "client", name, status, peer?, client?, group, isInNodeRead, count, errors, sumMs,
             buckets: int[15], p50Ms?, p95Ms?, p99Ms?, byHour: HourSeries[] }
HourSeries { hour: Timestamp, count, errors, p95Ms?, buckets?: int[15] }
```

- A series is one `kind`, `name`, and `status` (and `peer` or `client`). The node guarantees what a requester could otherwise choose: a name is at most 120 characters with no control character, `?`, or `#`; a route of `serve` or `client` begins with one of `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`, or `OTHER` (any other method) and a space, and a request that matched no route is the one series `unmatched`; a node that has no room for another series in an hour (500 of them) records it under `overflow`, and a name that was none of these under `invalid`; `status` is one of the set of its kind (`serve`: the four classes; `call`: the classes and `ok`, `error`, `timeout`; `client`: the classes and `network`); `peer` only for a call, `client` (`web` or `ios`) only for, and always for, what a client reported. `serve` is a route this node answers, named by its route template (`GET /api/orgs/{org}/teams/{team}/usage`), never by a path with ids in it; `status` is the class of the HTTP status (`2xx`, `3xx`, `4xx`, `5xx`). `call` is a call this node makes (`peer get_view`, `runtime view`, `runtime decide` (a decision applied to the team's runtime, as the background task does it, including the time the runtime takes), `apns send`, `github graphql`); `status` is `ok`, `error`, or `timeout`, and for a peer the class of its HTTP status; `peer` is the host of the peer's origin, which stays on the node. `client` is what a client observed and reported to its home node (`client` is `web` or `ios`; `status` the class, or `network`).
- **`group`** is what a screen draws a series under, said by the node so that no screen holds a table of its routes. For a route (`serve`, `client`) by its template: `desk` (`/api/me`, `/api/session`, `/api/decisions`, `/api/about`), `teams` (an org, its history, and what is under `/api/orgs/{org}/teams/`), `usage` (usage and budget), `evaluation` (evaluation and effort), `outcomes`, `devices`, `push`, `federation` (`/fed/v1/`), `metrics`, `unmatched`, and `other` for what is none of these (and for `overflow` and `invalid`). For a call by its first word: `runtime`, `peer`, `push` (`apns`, `webpush`), `github`, and `other`.
- **The budget.** An in-node read is held to a 95th percentile of at most `budget.inNodeReadP95Ms` (100) milliseconds in the reference environment the project names (an Apple silicon Mac or a four-core Linux machine, on loopback). `isInNodeRead` says which series it applies to, so that no screen decides: a `serve` GET of the desk, the devices, the push settings, the outcomes the owner entered, an org, a team's view, and, between nodes, an org's about and versions and a team's view. What calls the team's runtime, GitHub, or a peer (usage, evaluation, activity) is not one, and neither is anything a client observed (its network is in it). A percentile is the upper bound of its bucket and 100 is a bound, so `p95Ms <= 100` is the test; a series with `count` above 0 and no `p95Ms` is slower than 30 000 ms.
- **Objectives.** The operator of a node can set objectives for it: `metrics.objectives` in `config.json`, a list of `{ "group": <a group of routes>, "p95Ms": <1 to 30 000> }` (at most 20, one for each group; `unmatched` is not a group to hold, and a value outside these stops the node at start and names it). The answer says how each stands over the range asked for, as `objectives`: the buckets of all the `serve` series of the group (every route and status of it) are added up, and the bucket of their 95th percentile is compared, since a duration is not known more exactly than its bucket: `state` is `met` when the upper bound of the bucket is at most `p95Ms`; `notMet` when the lower bound of the bucket (the bound before it, 0 for the first) is at or above `p95Ms`, so that every duration in it is over, which includes one slower than 30 000 ms (that has no `measuredP95Ms`); `undetermined` when `p95Ms` falls inside the bucket (a 95th percentile in (50, 100] against an objective of 75 ms), which a screen says as that and not as met or not met; and `unknown` when the group had no calls in the range. `measuredP95Ms` is the upper bound of the bucket. The field is left out when there are no objectives, and in an answer narrowed by `kind` or `name`, which would not be the whole of a group. The node says it so that no screen compares.
- Nothing holds a request body, a token, an email, an address, a header, or a query string. A name is a template or a fixed phrase.
- Durations are kept as a histogram with fixed buckets: a duration falls in the first bucket whose upper bound, in milliseconds, it does not pass: 1, 2, 5, 10, 25, 50, 100, 250, 500, 1000, 2500, 5000, 10 000, 30 000, and a last bucket for what is slower. `buckets` has these 15 counts and adds up to `count`; `sumMs` adds up the durations.
- `p50Ms`, `p95Ms`, and `p99Ms` are the percentile by nearest rank (`ceil(n x percent / 100)`-th of the sorted durations), each given as the **upper bound of its bucket**: a duration is not known more exactly than its bucket, and an answer does not claim more. A percentile that lies in the last bucket has no bound and is left out, as is any percentile of a series with no durations: a series with `count` above 0 and no `p50Ms`, `p95Ms`, or `p99Ms` has that percentile beyond 30 000 ms.
- `errors` is the number of the `count` that were errors: a 5xx, a call that failed (`error` or `timeout`), or what a client lost to the network. A series has one status, so its calls are all errors or none are: `errors` is `count` for a `5xx`, `error`, `timeout`, or `network` series, and 0 for the others.
- `byHour` is the same series by hour of UTC, oldest first; hours with no call may be left out. An hour has `buckets` (the same fifteen counts as a series, adding up to the hour's `count`, and its `p95Ms` is their percentile) only in an answer asked for them with `hourBuckets=1`, so that a reader can add the hours of several series and read the percentile of their whole; without it the answer holds none, and it is the same as one that never had them. `hourBuckets` is `1` or left out, anything else is a 400; for a range of more than 7 days there are no hours to have them. `from` and `until` are the start of the first hour and the end of the last. `series` is ordered by kind (`serve`, `call`, `client`), then name, then status, then `peer`, then `client` (a series without one first).
- **What a client reports.** A client of the owner sends what it observed with `POST /api/telemetry`: `{ client, samples }`, at most 200 samples and 16 KiB, in one request. A sample is `{ route, status, ms }`: the route as the node names it (`GET /api/orgs/{org}/teams/{team}/view`), the class of the status or `network` for a call that got no answer, and the whole milliseconds from the start of the request until its body was read (or the failure came; a call the client itself cancelled is not reported). The routes a client may name are listed in `testdata/route-templates.json`, which a test holds to the node's own table and the table to the router, so that a client names a route from the file and a renamed route fails a test. The node keeps a sample as a `client` series of its `client`, and drops, counting it in `dropped`, a sample whose route is not in the file (an id in a path, a query, another node's route, the node's own `POST /api/telemetry`) or whose status is not one of the five; it never makes a series for a text a client chose. A `ms` above 30 000 counts as 30 001, in the last bucket. A report that is not well formed is refused whole. The version of the client is not in it: `x-agency-client` notes it. The call that reports is timed like any other (`serve`, group `metrics`).
- The shared sample is `testdata/metrics.sample.json`; a test reads it back unchanged and checks that every series agrees with itself (15 buckets that add up to `count`, the percentiles those of the buckets).

## Client API

A client (web, iOS, desktop) talks to its home node under `/api`. The node answers as its own account: only orgs that account belongs to are visible, and anything else is 404. A **guest** is the exception (below).

**Guests.** A member this node hosts (`people[].hostedBy: "root"`, see "Org definition") has no node of its own, and its clients talk to this node signed in through Access as that member.
- The node keeps, in `guests/` of its data directory and never in the definition, which sign-in email is which hosted member of which org (lowercased, compared exactly). It admits an Access sign-in as that guest only while this node is the org's root and the definition still lists the member as hosted; otherwise the sign-in is what it was before. The owner's email (`access.ownerEmail`) always wins: the owner is never a guest. A direct local request is never a guest.
- A guest reaches only these routes, and every other one answers it 403: `GET /api/about`, `/api/session`, `/api/me`, `/api/devices`, `/api/decisions`, `GET /api/orgs/<its org>/teams/<team>/view`, `POST /api/orgs/<its org>/teams/<team>/envelopes`, `POST /api/devices/requests`, `POST /api/devices/changes`, the push routes (`GET`, `POST /api/push/tokens`, `DELETE /api/push/tokens/<token>`, `GET /api/push/vapid`, `GET`, `POST /api/push/subscriptions`, `DELETE /api/push/subscriptions/<id>`); and `GET` (or `HEAD`) of the web client itself, any path outside `/api`, `/metrics` and `/app`, which holds none of the node's data, so that the client's guest shell runs. The app sign-in (`/app/handoff`, `/app/callback`) is not a guest's yet. Reads are checked against this list before the route; writes by the guest's own case of the write check, which sends nothing on to the owner's.
- What it reads is its own: `/api/me` has its member as `account` (with an empty `fingerprint`: it has no account key), its org only, with only the teams on this node that address it (by a runtime name, or through a seat or external party it answers for), `funding` `[]`, and `guest: { member, org }`, and no `homeNodes`, `rootChanges`, or org `recovery`; a client draws no funding for a guest. For anyone who is not a guest, `guest` is **left out**, never `null`, `false` or `{}`: a client treats any `guest` that is there as a guest, so that an odd shape gives less, not more. A team's view is the answerer's view (only the requests it answers; no people, work, or epics), and only of a team on this node that addresses it (404 otherwise). `/api/devices` lists its own devices and the requests that ask to be added for its member, never the owner's and never another guest's, and no `node`. `/api/decisions` lists its own decisions, never the owner's, and the owner's list never shows a guest's: each logged decision keeps the member who made it (`by`).
- Its notices are its own. An APNs token or a browser subscription a guest registers is kept as that guest's (`PushToken.guest`, `{ member, org }`, left out for the owner's), and gets only `request` notices whatever kinds it asks for. A guest lists and removes only its own (removing another's, like an unknown one, is 204 and changes nothing). A token or browser kept as someone else's, the owner's or another guest's, is not taken over: registering it is 409 for either side. The `device` a guest's registration names is one of its member's current devices in the guest's org (400 for any other, the owner's included), and the registration is dropped once that member no longer has the device, as the owner's are with the account's. A guest is told once of each request that starts waiting for its member in a team on this node, by the same rule as its team view; its badge is the number of those requests; titles follow `hideTitles`. Its first pass only records what waits. The owner's notices, desk refreshes and retries never go to a guest's destinations, and a guest's never to the owner's. A guest whose member is no longer hosted, or whose org this node no longer roots, is told nothing. A guest's notice whose destinations all fail is sent again on the next pass, not retried alone.
- What it writes is as its member: an envelope whose `account` is the guest's member, signed by one of that member's devices (403 for any other account), in a team on this node that addresses it (404 for any other, so a guest's decision is never relayed to another node and logged for a seat it does not answer for), a request that a device of its own asks to be added for its member (`POST /api/devices/requests`, kept for that member alone, an hour and at most 10, as the owner's are; the owner's `/api/devices` never lists it and the terminal does not either), and a device change for that member in its org, with which one of that member's devices approves such a request.
The types are in `agency-proto` (`client.rs`) and generated into `bindings/`.

**`x-agency-client`.** An app tells the node which release it is, on every call: `x-agency-client: <platform>/<version> (<build>)`, for example `ios/0.3.0 (202611260418)`.
- `platform` is `ios`, `macos`, or `android`, in lower case. `version` is exactly three decimal numbers separated by dots, of at most 6 digits each (`MAJOR.MINOR.PATCH`). `build` is optional, with one space before its parenthesis, and only decimal digits: an unsigned 64-bit integer (a TestFlight build is a UTC time to the minute, 12 digits). The whole value is at most 64 characters. An app with no version leaves the header out, and one whose build is not all digits leaves the parenthesis out.
- It is **informational**: a request without it, or with a value that is not exactly this form, is served as before and the value is ignored, never refused. The node reads it only on requests it **admitted**, so a stranger cannot make it record anything.
- The node keeps, in `clients-seen.json` of its data directory, for each platform and version, when it last admitted a request with it and the build then, and no more than the 32 versions seen most recently for a platform. It notes a version at most once an hour. It holds nothing about the person, the account, or the device, and `agency status` lists it. It is the fact that `oldestApp` in discovery rests on, when a breaking Client API change needs a floor.

### Push notifications

When `push` is configured (`keyPath` of an APNs `.p8` key, `keyId`, `teamId`, `bundleId`), the node notifies the owner's registered push tokens through APNs. Without it, nothing is sent.

- **What a notice says is printable.** Every text in a notice that someone else wrote (a team's label, a request's title, a device's label, a refused decision's title, the words of a held change) is sent, through APNs and Web Push alike, with each character `is_hidden_char` names, a line break included, as `?`. A notice is shown on a lock screen and in a browser's notification, where such a character could make a line say something it does not.
- The node checks every 30 seconds for three kinds of news, each one told once: a **request** waits for the owner, a **device** asks to be added, or a **decision** of the owner's is refused. A token gets the kinds it registered with (`events`), and a kind no token wants is recorded and sent to nobody.
  - `request`: it waits for the owner when it is the owner's to decide, by the rule in "Requests" (the same set as `TeamSnapshot.mine`, with the same limit for teams on other nodes). Its key is `org/team/request id`.
  - `device`: a device request (see "Devices") that was not waiting at the previous check, by the device's id (`d-` and its pairing code), so the same key asking again is the same device. Its key is `device/<device id>`.
  - `decision`: a decision in the decision log whose state is now `refused` and was not at the previous check, by the decision's id. A decision that was queued and is refused later is told when it is first seen refused. Its key is `decision/<id>`.
  - `recovery`: a recovery of an org whose `root.account` is the node's account was started and waits (see "Recovery key"), by the org and the start's version. Its key is `recovery/<org>/<version>`. Unlike the other kinds, **every token and every browser subscription gets it, whatever kinds it names**, and it is told on the node's first check too, which records the other kinds unsent: the owner can cancel a recovery only while it waits. Its alert is written by the node, not by the app: `{ "title": "A recovery of <org> was started", "body": "It takes effect at <time>. If you did not start it, sign any version of the org now, for example with agency root-cancel-recovery." }`, with `"thread-id": "recovery/<org>"`, `apns-collapse-id` the org's id, and `agency: { "type": "recovery", "org", "startedAt"?, "finishesAt"? }`: when this node took the start and when the recovery takes effect on it (ISO 8601, the same time as `/api/me`'s `takesEffectAt`), both left out when the node keeps no record of the start. A browser gets the same. A client words the notice in its own language from these facts; the node's English `title` and `body` are for one that does not know the kind. It names the org by id, never by label, so `hideTitles` leaves it whole.
  - `root`: a change someone asked the root to sign is held for the owner (see "Pending root changes"), by its handle. Its key is `root/<id>`, the id described below, never the handle. A token or a browser that names `device` gets it too, since a device to approve is the usual case. Its alert is written by the node: `{ "title": "A change to <org> waits for the root key", "body": "<what it changes>. Run agency root-sign on the root key's node to sign it." }`, with `"thread-id": "root/<org>"`, `apns-collapse-id` that id, and `agency: { "type": "root", "org", "id", "waiting" }`, where `id` is 16 hex digits of SHA-256(`agency/push-id/v1` followed by the handle), never the handle, and `waiting` is how many changes wait in the org; with `hideTitles`, the body leaves out what it changes, which names a member's or a device's label. A browser gets the same `title` and `body`.
- **A destination that failed is tried again, alone** (agency#284). A notice counts as told once it has been tried: the phone and every browser that wanted it are sent it, and each one that failed (not gone) gets a retry of its own, kept in `push-retries.json` of the data directory as the notice's key, the destination (a token, or a subscription's id), and when it first failed; **no title, label, or other word is written**. At each check the node first sends again to each retry's destination only, making the notice again from what is true now and with the settings of now (`hideTitles` included). A retry ends when the destination took the notice or is gone (removed as above), is no longer registered or no longer wants the kind, **the thing is no longer true** (the request no longer waits for the owner, the device request is closed, the decision is no longer refused: a notice about what has passed is never sent late), or it is a day old; at most 1000 are kept, the oldest first dropped. A destination registered after a notice was told is not sent it. So a browser whose push service had a bad minute is not forgotten because the phone took the notice, and one that took it is never sent it twice.
- The node remembers the last 1000 keys of each kind. The first check after the node starts with an empty data directory only records what is there. A node that held only request keys records the device requests and refusals it finds the first time, and does not send them.
- A request's notification is `{ "aps": { "alert": { "title": <team label>, "body": <request title> }, "sound": "default", "thread-id": "<org>/<team>", "badge": <count> }, "agency": { "org", "team", "request" } }` with `apns-collapse-id` set to the request id. `badge` is the number of requests waiting for the owner across all their orgs and teams when the notification is sent, this one included: the sum of `mine` over the teams whose view the node could read. The other kinds carry the same `badge`, which a device or a decision does not change.
- **Waking the app to read the desk.** The iPhone app shows widgets that read a small file the app writes after it reads the desk, so while the app is closed a request that arrives or is decided is on the widget only when the app is woken. A request's alert therefore also carries `"content-available": 1` in `aps`; a device's or a decision's does not, because they do not change the desk. A change of the desk that no alert covers (a request decided, or one that left the owner's desk, or a request whose alert no token wants) is told by a push of its own to every registered iPhone token, whatever kinds it chose: `{ "aps": { "content-available": 1 }, "agency": { "type": "desk", "node": <id> } }`, with `apns-push-type: background`, `apns-priority: 5` (Apple refuses 10 for it), `apns-collapse-id: desk`, and `apns-expiration` one hour after it was made. It carries no alert, sound, badge, title, label or count (the id of the node apart): the app reads the desk itself. The node keeps the sorted keys of the requests that waited for the owner when it last woke the iPhones, and when (`desk-refresh.json` in the data directory). It sends when those keys differ, at once after a quiet time and at most once in 15 minutes: a change inside the window stays pending and goes when it ends, so changes inside one window go together and a desk that comes back to what it was sends nothing. An alert that an iPhone accepted counts as the wake for its change, and so restarts the 15-minute window like a push of its own. A push that fails restarts the window too, with the change still pending, so a node whose pushes fail tries again after 15 minutes and not at every pass (4 times an hour); tokens APNs no longer accepts are removed as for an alert. The first pass only records. A node without an APNs key sends nothing, and a browser's subscription gets none of this (Web Push has its own path).
- A device's alert is worded by the app: `{ "loc-key": "PUSH_DEVICE_WAITING", "loc-args": [<device label>] }`, with `"thread-id": "devices"`, `apns-collapse-id` the device id, and `agency: { "type": "device" }`. Only the label travels, never a key or a code. A refused decision's is `{ "loc-key": "PUSH_DECISION_REFUSED", "loc-args": [<the request's title>] }`, with `"thread-id": "<org>/<team>"`, `apns-collapse-id` the decision id, and `agency: { "type": "decision", "org", "team", "id" }`. A request has no `type`.
- When a title or label is missing (a decision logged without a title) or hidden, the alert names a string that takes no argument: `PUSH_DEVICE_WAITING_NO_LABEL`, `PUSH_DECISION_REFUSED_NO_TITLE`, and, for a request, `PUSH_REQUEST_WAITING_HIDDEN` (with no title, label, or `loc-args`). `"hideTitles": true` in `push` hides every title and label of every kind this way, for a node whose data must stay where it is. The app ships all these strings.
- **The node names itself** (agency#117). Every APNs push, the desk wake included, carries `agency.node`: the id of the node that sent it, so that an app that has several home nodes opens a tapped notification on the right one, and sums their counts for the one number on its icon. (Web Push payloads do not carry it: a browser subscription belongs to one origin.) The id is the first 16 bytes of the SHA-256 of the UTF-8 text `agency-node:` followed by the node's origin, written as 32 lowercase hex characters. The origin is the node's `url` written one way: `https://<host>[:<port>]` (or `http://` on a loopback address), the host in lower case, the port left out when it is the scheme's default, no path, query or user name (the same rule as the addresses in `homeNodes`). `testdata/node-id.json` pins it, with the same address written in several ways, and the apps work out the same id for each node they know. It is not a secret and not the host name: a push passes through Apple, and the name of the owner's host does not need to. A node whose `url` is not a home node's origin leaves the field out, and an app then takes the push for the node it has open. Every alert (not the desk wake) also carries `"mutable-content": 1` in `aps`, so that the app's notification service extension can set the badge to that sum; the `badge` the node sends stays this node's own count.
- Nothing else about a request, a device, or a decision leaves the node.
- **A registration may name its device.** A push token or a browser's subscription may carry `device`, the `id` of one of the account's devices (`Device.id` in an org definition). The node accepts it only for a **current** device: one in the account's entry of any org it belongs to (400 otherwise), so that a registration cannot name a device that was removed, or one that was never the account's. When the node writes or learns an org definition in which the device is no longer there (a removed device, or an account that left), it drops every registration that names it, and logs that with the device's id and the counts, **never the token, the endpoint, or a key**. A registration that names no device (every one made before `device` existed, and any a client makes without it) stays until it is removed by hand, so a client that wants a lost device cut off sends its `device`. A node lists `pushDevice` in its `capabilities` (see `docs/compatibility.md`); a client that sends `device` to a node that does not list it gets 400 for the unknown field.
- A token APNs answers 410 or `BadDeviceToken` for is removed. Any other failure is tried again at the next check. The provider token (ES256 JWT, `kid` the key id, `iss` the team id) is reused for 50 minutes.

#### Web Push

When `webPush` is configured (`{ "subject"?, "extraHosts"? }`), the node also notifies the owner's browsers (RFC 8030, 8291, and 8292), with the same kinds, the same once-only rule, and the same notices as above, to each subscription that wants the kind. The iPhone keeps its app and APNs; a browser on iOS is not served.

- The node makes a P-256 VAPID key the first time it is needed and keeps it in its data directory (`web-push-vapid.key`, readable by its account only: the node does not use, and says so at start, a key file that other accounts can read), never in `config.json`. A subscription records the `keyId` it was made with, and is sent nothing while the node's key has another (its push service would refuse it): the client says "subscribe again", and registering the same endpoint again replaces it.
- A message is the notice as JSON, encrypted to the browser with `aes128gcm` (RFC 8291) and sent as a POST with `TTL: 3600`, `Urgency` (`high` for a request, else `normal`), `Topic` (a hash of the request's, device's, or decision's key, at most 32 characters), and `Authorization: vapid t=<JWT>, k=<public key>` (ES256, `aud` the push service's origin, `exp` 12 hours on, `sub` the `webPush.subject` (a `mailto:` or `https://` address, or the node does not start Web Push), else the node's public host name, else its origin; Apple's push service refuses a contact that is not `https` or `mailto:`, so a node with neither `subject` nor `access` says at start to set `webPush.subject`). The push service sees only ciphertext. The message is `{ "agency": { "org", "team", "request" } or { "type": "device" } or { "type": "decision", "org", "team", "id" }, "badge": <count> }`, with `"title"` (the team's label) and `"body"` (the request's title) for a request, and `"detail"` (the device's label, the refused decision's title) for the other two. A title, a label, or a detail is cut at 200 characters, and is left out when it is missing or hidden: a client then words the notification by its kind, and shows nothing else.
- `"hideTitles": true` at the top of `config.json` hides titles and labels for every kind, in every notification, APNs and Web Push alike (`push.hideTitles` is still read and means the same): both go through a service that is not the node's own.
- **Where the node sends.** The node sends a message only to an endpoint that is `https`, has no user information, no port, and no fragment, is a host name and not an address, and is on the list: `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `*.push.apple.com`, `*.notify.windows.com`, and `webPush.extraHosts` (a name, or `*.` and a domain; an address is never allowed). It is checked when the subscription is registered (400) and again before each send (the subscription is then removed). The node resolves the name itself and connects only to an address on the public internet (not loopback, private, link-local, shared, documentation, multicast, or reserved), so a name that later points inside the network is refused too. It follows no redirect, sends no cookie or credential besides the VAPID header, and gives up after 10 seconds.
- **What `sub` tells the push services.** The contact in the VAPID header is read by the operators of the push services (Google, Mozilla, Apple, Microsoft), so it names this node to them: by default the node's public host name (or its origin). `webPush.subject` can be a less specific address, such as a `mailto:` alias made for this, and a personal address is only ever what the owner writes there.
- **At once, and what a notice carries.** The node sends to up to four subscriptions at once, so that a push service that is slow (each is given 10 seconds) does not hold the others, nor the iPhone's notice; the answers are matched to the subscriptions in their own order. The `request` and the `id` in `agency` are strings a runtime chose: they are sent only when they are plain identifiers (letters, digits, `.`, `_`, `-`, at most 200 characters, not `.` or `..`) and are left out otherwise, and the notification then opens the desk.
- An answer of 404 or 410, a subscription whose keys are not a browser's, or an endpoint that is no longer allowed removes the subscription. Any other failure (429, 5xx, a timeout) is tried again at the next check, to that subscription alone (see "A destination that failed is tried again" above). The node never logs an endpoint or a key.

### Who is let in

The node serves the federation routes, the Client API, and the web client on one port. The federation routes are checked only by signatures. The Client API and the web client admit a request only when:

1. it is direct and local: the TCP peer is a loopback address, `Host` is `127.0.0.1:<port>` or `localhost:<port>`, and there is no `cf-ray` or `cf-connecting-ip` header. Any other `Host` gets 421, and a peer beyond loopback gets 403. The peer check is needed because the node may listen beyond loopback for federation, and the sender chooses `Host`. With `"localClients": false` in `config.json` (default `true`), every such request gets 403 instead: on a machine that other accounts log in to, each of them reaches the loopback address the same way. The federation routes answer either way; or
2. it comes through Cloudflare (those headers) or names the configured public host name, and carries a valid Cloudflare Access JWT in `Cf-Access-Jwt-Assertion`: RS256 only, signed by a key from `https://<team domain>/cdn-cgi/access/certs` (fetched again for an unknown key id, at most once a minute), the configured audience, issuer `https://<team domain>`, and `exp`/`nbf` within 60 seconds. Without an `access` setting, or with a malformed one, these requests get 403. A valid token admits only a known identity: the configured `ownerEmail`, or a current guest's email (see "Guests"). Any other sign-in, one with another email or with none (a service token), gets 403 on every route, reads and the page included; nothing is admitted by default.

Before any of this, and before routing, a request whose path holds an encoded separator (`%2F` or `%5C`, in either case), a backslash, or a dot segment (`.` or `..`, also as `%2E`) gets 400, on every route, federation ones included: such a path could be resolved differently by a layer in front of the node and by the node itself.

Writes (any method but GET and HEAD) also need:

- the page's token in `x-agency-token`. The node picks a random token at each start and writes it into the served `index.html` in place of the placeholder `content="__AGENCY_TOKEN__"` of `<meta name="agency-token">`. A page on another site cannot send this header without a preflight, which the node never allows;
- `Content-Type: application/json` (except for DELETE, which has no body) and a body of at most 64 KiB;
- through Access, the signed-in email must equal the configured `ownerEmail`, because writes act for the node's account: they relay its decisions and its device changes, and ask to add its devices;
- on a node with an `access` setting, even a malformed one, a direct local request may read but never write (403): the owner is who Access says it is, so a process of the same OS user on the node's machine cannot write as the owner. Without `access`, a direct local request is the owner, since nothing else could be; such a node protects nothing from processes of the same OS user.

The node serves `web/dist` (built into the binary) for every other path, falling back to `index.html` for the web client's own routes. Pages carry `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and `Cache-Control: no-store`.
A node with an `access` setting adds `Strict-Transport-Security: max-age=31536000` (no `includeSubDomains`) to every answer, so browsers reach its public host name over HTTPS only. A node without one whose `url` is `https://` adds it to every answer to a request that came through Cloudflare (`cf-ray` or `cf-connecting-ip`), refusals included, since that is how browsers reach it at its public host name; a direct local request gets none.
If Cloudflare Access protects the node's public host name, its policy must bypass `/fed/*`, because other nodes authenticate with signatures, not with Access, `/.well-known/apple-app-site-association`, because Apple's servers fetch it without signing in, and `/app/redeem`, because the app has no Access sign-in when it asks for the token (see "App sign-in").

### App sign-in

A web view in the iOS app cannot use passkeys for the Access team domain, so the app signs in to Access in a system browser session and takes the session over. This needs the optional setting `access.appId` (and, for the custom scheme, `access.allowSchemeSignIn`, below), the app identifier `<team id>.<bundle id>` (ten uppercase letters or digits, a dot, and a bundle id of letters, digits, dots, and hyphens, for example `ABCDE12345.com.example.agency`). Without it, or with a malformed one, `GET /app/handoff` and the association file answer 404; the rest of the `access` setting still applies.

- `GET /app/handoff?state=<state>&challenge=<challenge>&via=<link|scheme>` is admitted like the Client API. The app makes a random 256-bit `verifier`, keeps it, and sends `challenge`, the unpadded base64url of its SHA-256 (43 characters, as `state` is). The node makes a `code` (32 bytes from the system's random source as base64url, 43 characters) that holds the verified `Cf-Access-Jwt-Assertion` and the challenge, lives for 60 seconds, and answers `303 See Other` with `Cache-Control: no-store` and `Referrer-Policy: no-referrer` and, for `via=link`, `Location: https://<publicHost>/app/callback#code=<code>&state=<state>`, or, for `via=scheme`, `Location: agency-signin://callback#code=<code>&state=<state>`. **The token is in no URL.** `link` is for a host in the build's associated domains (a universal link, which only the app named in the association file receives); `scheme` is for any other host, where another app may have registered the same scheme: a callback that was read is then useless, because the code is worth nothing without the verifier, which never left the app. The scheme is **off unless `access.allowSchemeSignIn` is `true`**: the callback goes to the app that started the session, whatever app that is. Without the setting, `via=scheme` answers `400` (no redirect, no code made, no place taken among the waiting codes); `via=link` and the deprecated form are not affected. The query must be exactly those three parameters in that order and nothing else (`via` is one of the two words; an unknown word, a missing or repeated parameter, a wrong length or character gets 400). A direct local request gets 403 (it carries no Access sign-in), and so does a signed-in email other than `ownerEmail`. The target is built only from `publicHost` or the fixed scheme; nothing else from the request goes into it. At most 64 codes wait at once (503 beyond). The codes are kept in memory: a restart of the node ends them. The node never logs the request URL or the answer's `Location`.
- **Deprecated, kept side by side (compatibility policy, #313):** `GET /app/handoff?state=<state>` alone, the form of the apps before the code exchange, still answers as it did: `303` to `https://<publicHost>/app/callback#token=<jwt>&state=<state>` (same headers, same owner check, the query exactly `state=` and 43 base64url characters, anything else 400). It is used only by an app that does not send a challenge. The node writes one line to its log when it is used (`agency: the app handoff was used in its deprecated form`; no URL, token or state in it), so the owner can see when no app uses it, and it will be removed after a release of the apps that speak the code exchange has been in use for a while. Do not build on it: it puts the token in a URL, which only a universal link makes safe.
- `POST /app/redeem` with `{ "code": <code>, "verifier": <verifier> }` (exactly those two members) answers `200` with `{ "token": <jwt> }` and `Cache-Control: no-store`, when the code is one the handoff made, has not been redeemed, is not 60 seconds old, and the SHA-256 of the verifier is the challenge it was made for (compared in constant time). It is not behind Access (the app has no Access sign-in when it asks for the token): what admits it is the code and the verifier. A code is tried once: it is taken out whatever the verifier says, so a wrong verifier burns it and the app starts the sign-in again. Every other way to fail (an unknown, used, expired or malformed code, a malformed or unknown-member body, a wrong verifier) answers the same `400` with the same body, so the answer says nothing about which. Each client address gets 20 tries a minute (`429` with `Retry-After` beyond, even for a good code); the address is `Cf-Connecting-Ip` when the peer is this machine (a tunnel), and the peer otherwise; at most 1024 addresses are remembered, and a new address beyond that makes the node forget the one that has been quiet the longest (its allowance starts again), so that filling the table cannot lock the owner out; what protects a code is its 256 random bits and that it is tried once, not the count. A node without `access.appId` answers 404. The Access policy of the node's public host must bypass this path (see above).
- `GET /app/callback` is the universal link of `via=link`, which the app receives before it loads. If a browser loads it anyway, it gets a page with no script that reads nothing from the URL, admitted like any other page.
- `GET /.well-known/apple-app-site-association` is served to anyone, without an Access sign-in, as `application/json` without a redirect: `{ "applinks": { "details": [{ "appIDs": [<appId>], "components": [{ "/": "/app/callback" }] }] }, "webcredentials": { "apps": [<appId>] } }`. Nothing in it comes from the request.
- A native client keeps the handed-over token and sends it in `cf-access-token`. Once Access no longer accepts it, Access answers with a redirect to the team domain instead of the node's answer. The client never follows that redirect; it treats it as signed out and runs the handoff again.

## Discovery

What a node says about itself, so that an app or another node can check what it speaks before relying on something new. The rules for what may change, and what each contract's rollout is, are in [compatibility.md](compatibility.md); this is the wire shape.

```
About        { node: string, contracts: Contracts, capabilities: string[], oldestApp?: { [platform]: string } }
Contracts    { federation: number[], signedText: number[], runtime: number[], clientApi: { current: number, oldest: number } }
```

- `node` is the node's release, `MAJOR.MINOR.PATCH`. `contracts` lists, for each contract, the versions this release speaks (two at once during an overlap); `clientApi` is the version it serves and the oldest it still serves.
- `capabilities` are **strings**, so that a reader ignores a name it does not know (a newer node may list one). The names this release knows, and what each means, are in the table of compatibility.md ("Capabilities"); they start at what came after the first release. A test fails when an optional field is added to the org definition without one.
- `oldestApp` (per platform, `ios` or `macos`) is the oldest app version the node serves, and is **absent while the node sets no floor**, which is until a breaking Client API change needs one. `GET /api/about` may carry it; the federation answer never does.
- Readers ignore fields they do not know in an `About`. A node keeps an answer only within limits: at most 64 entries in a list (versions of a contract, capabilities, platforms) and at most 64 characters, without control characters, in any text of it.
- A node keeps what it reads of each of the org's other nodes in `about/<org>.json` of its data directory, with when it read it and, if the last try failed, why (see compatibility.md, "Discovery", for when it reads again).
- `GET /api/about` is admitted like any Client API read. `GET /fed/v1/orgs/<org>/about` is a member's signed read of the org (checked as in "Signed reads", against that org's members, which is why the path names the org), so a stranger cannot learn a node's version. The shared sample is `testdata/about.sample.json`.

## Test vectors

`testdata/vectors.json` holds keys from fixed seeds and the canonical JSON and signature of fixed bodies. The account key (seed `07…`) signs an org definition and a first-device change. The device key (seed `09…`, with its pairing code) signs a decision envelope and a comment (text without a choice). `canonical` lists values with the canonical text each must become: non-ASCII and astral characters, quotes, backslashes, slashes, control characters, U+007F, U+2028, precomposed next to decomposed characters (never normalized), keys whose UTF-8 order differs from their UTF-16 order, nulls, and integers. Ed25519 signatures are deterministic, so a client that imports the same seed (for example through WebCrypto) must produce the same signatures. `p256Device` is a P-256 device key (private scalar `0b…`) with its text, fingerprint, pairing code, and device id, and its signature over the comment's signed text. `deviceChangeP256` holds two device changes signed by that P-256 device: an add with a nested `device` (a second P-256 key) and a remove with a bare device id, each with its canonical JSON, its signed text (`agency/v1/device\n` and the canonical JSON), the signer's device id, and the signature, and the signer's key as `signerKey`. ECDSA signatures from other signers differ byte for byte; a client checks that these verify and that its own signature over the same text verifies with the key.
`rootRotation` moves that org to a new root key (seed `0d…`): `namingTheNewRoot` is version 2, which names the new key and is signed by the old one, and `signedByTheNewRoot` is version 3, signed by the new one.
`rootRecovery` gives that org a recovery key (seed `0e…`) in `addingTheRecoveryKey`, signed by the root. The recovery key then signs `start` (naming a new root key, seed `0f…`) and `finish`; `cancel` is the root-signed version that takes the finish's place instead. `replacingTheWordsStart` and `replacingTheWordsFinish` move the recovery key to a new one (seed `10…`) the same way. `refused` lists versions that `verify_successor` refuses, each with the version it follows and the reason.
`signedRead` has the account key sign a read of `/fed/v1/teams/acme/app/view` in both texts: `unbound` (`agency/v1/read`) and `bound` (`agency/v2/read`, with the `audience` it names, the node id of `https://work.example.com` from `testdata/node-id.json`). Each has the `text` signed and the `signature`. A signature of one is no signature of the other, and the bound one fails for any other audience.
An implementation in another language must produce the same values.

`testdata/client/` holds the Client API's answers as two test nodes give them: alice's, which hosts `acme/app`, and bob's, a member that reads it as a replica. The nodes use fixed keys, counted ids, a fixed clock, and fixed ports, so the files repeat byte for byte. `cargo test` fails when a file differs from what the node answers; `AGENCY_WRITE_FIXTURES=1 cargo test -p agency-node --test fixtures` writes them again. Clients decode these files in their tests, so a change to an answer shows up as a change to a file. Besides the plain answers, it holds `me-funding.json` (`/api/me` with two funding sources), `usage.json` (a team's token usage), `device-change-result.json` and `device-change-result-queued.json` (a device change the root's node applied, and one queued while it is down), and `device-list-p256.json` (devices with an Ed25519 and a P-256 key, and a pending request from a P-256 key).
